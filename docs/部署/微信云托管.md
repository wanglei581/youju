# 部署：微信云托管 + 云托管自带 MySQL（#32 草案）

> 状态：草案。镜像还没有构建验证过（本机没有 Docker），开通云托管后第一次构建时验证，结果补在本文。
> 依据：微信官方文档（2026-09-28 本机直接访问核对），链接见文中。
> 数据库：创始人决定先用免费的（D-022），用云托管自带的 MySQL 8.0，不另买腾讯云 PostgreSQL。

## 一、结构

| 服务 | 用途 | 公网 | 实例数 | 环境变量 `YOUJU_ROLE` |
|---|---|---|---|---|
| 小程序接口 | 小程序全部接口（`/api/v1/*`） | **关闭** | 按量伸缩，最小 0、**最大 3**（导出按实例限次数和并发，实例数有上限才封得住资源用量；首批试用足够，用户多了再调）。空闲约 25 分钟后缩到 0，再打开要等约 67 秒（10/12 实测）；创始人不加最小实例（要花钱），首屏改从常驻的 admin 取快照，见第六节 | `api` |
| 核对台和定时任务 | 截止日期核对台、管理接口；每天定时检查栏目、补详情、抽截止、解析名单 | 开启（只挂核对台和管理接口，用口令） | **固定 1 个** | `admin` |

两个服务用同一个镜像（仓库根目录 `Dockerfile`）。

- **为什么小程序接口关闭公网：** 小程序用 `wx.cloud.callContainer` 调用时，服务收到的请求头自动带用户身份（`X-WX-OPENID` 等），官方建议只有小程序调用的服务关闭公网访问，并用 `X-WX-SOURCE` 判断来源（[容器内变量信息](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/development/weixin/index)、[调用云托管服务](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/development/call/mini.html)）。关闭公网后，别人无法伪造用户身份头。
- **为什么定时任务服务固定 1 个实例：** 云托管没有单独的定时触发器，官方做法是在容器里跑 cron（[定时触发](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/practice/trigger.html)）。多个实例会各跑一遍，缩到 0 个实例则不跑，所以固定 1 个。
- **限制：** `callContainer` 请求不超过 100 KiB、返回不超过 1000 KiB（导出文件要控制在这以内）；小程序基础库最低 2.23.0。

| 每周四 07:30（周五到周日补跑） | `job.sh weekly-digest --kind reminder --scheduled` | 按方案生成“临期提醒”：未来 7 天内截止、截止日期已人工核对的申报项目；本周已生成的跳过；和周报同一行依次执行（共用任务锁） |
| 08:00 | `youju audit-deadlines --sample 20` | 质检已发布的截止日期：规则回查全部（早于发布日期、正文缺失、正文里找不到这个日期），配了 AI 时再抽查 20 份；存疑的和 AI 出错的提醒到群里，在核对台"质检存疑"页复核（确认无误或退回待核对） |
| 08:00 质检做完后 | `youju daily-report` | 运维日报发到群里：今天栏目检查、24 小时新文件和补详情、新截止候选、核对进度和待办（待核对、30 天内截止、类型待定、质检存疑、纠错）、用户总数、昨天的 AI 用量和费用；配了 AI 时附上 AI 建议先核对的 3 份通知。`--dry-run` 只打印不发 |

抓取规则不变：YoujuBot 标识、遵守 robots、每站 3 秒、遇拦截即停。同一任务不重叠（上一次没跑完就跳过这次并提醒），单次最长 3 小时，超时算失败并提醒。

AI 任务（`advisor-run`，admin 每分钟一次，表里没列）：
- 队里有任务就一直领，和原来一样领到空为止。
- 队里空了以后，开始后的 50 秒里每隔 3 秒再看一次；50 秒以后，只要别的线程还在做任务，也接着看。这样用户点了几秒内就开始。原来每分钟只领一次，10/27 实测排队 48.6 秒。
- 开始满 4 分钟不再领新的，手上的做完就退出。所以一轮最长约 4 分钟加一个任务的时间（任务最长 5 分钟）。
- 数据工具（批量工具）那条路不轮询，同样满 4 分钟不再领新的。处理它的整段时间也算"有人在忙"。
- 一轮常会跨过下一分钟。下一分钟那一次最多等 55 秒，上一轮一结束就接着跑。等满 55 秒还没轮上时：
  - 上一轮开始不到 10 分钟，就安静跳过，不算失败；
  - 超过 10 分钟、读不到开始时间、或者时钟往回调过，就当作卡住了，照常提醒"上一次还没跑完"。
- 手动跑用 `youju advisor-run --once`：只把现在排着的处理完，不等新任务。任务日志打到容器标准输出，在云托管"服务日志"里看。提醒渠道待创始人确定；配置企业微信群机器人后，可用 `youju alert "测试文本"` 验证。`check-sources` 已发送详细提醒时，任务包装器不再重复发送通用失败提醒。

数据库迁移只在 admin 服务启动时执行，并用 MySQL 命名锁（`GET_LOCK`）：滚动发布时即使新旧两个实例同时启动，也只有一个在迁移。

发布顺序：平时先发 admin（迁移建好新表、新列），再发 api。**删表、删列的迁移反过来**（如 0035）：

- 先发 api（新代码已经不用这些表和列，在旧结构上照样能用），用 `tools/team/cloud-versions.cjs` 看到旧版 api 归零后再发 admin（启动时迁移）。反过来的话，迁移删列以后、新 api 上来之前，旧 api 查用户都会报列不存在。
- 迁移完成后旧版 admin 还会跑约 14 分钟，cron 照跑：每分钟的 advisor-run、pay-run 没活的时候不读用户表，不受影响。要是正好有任务被旧版领到，读用户会报列不存在：名单比对、客户相关通知表这两种数据工具任务重新排队，连续 3 次被旧版领到才失败、退回次数；AI 解读、条款对照任务直接失败、退回次数。pay-run 有订单要处理时也会出错。所以发 admin 之前先确认三件事：没有排队、正在处理的任务（在数据库管理里执行 `SELECT status, COUNT(*) FROM advisor_tasks WHERE status IN ('queued', 'running') GROUP BY status`，没有结果才发）；`pay_orders` 里没有 pay-run 要处理的订单（在数据库管理里执行 `SELECT status, COUNT(*) FROM pay_orders WHERE status IN ('pending', 'refunding') OR (status = 'manual' AND alerted_at IS NULL) OR (status = 'completed' AND goods_notified = 0) GROUP BY status`，没有结果才发；支付开着也可以发，但从发 admin 到旧版 admin 归零这段时间里不要下单、不要申请退款）；避开 03:30 到 04:45（清理、备份、校验，旧版 admin 跑这几个会失败）。发布后约 15 分钟里不要提交任何批量任务和 AI 任务。
- 迁移要等 `users` 表的元数据锁：有事务读过 `users` 还没结束（例如批量任务正在处理）时，最多等 5 秒就失败，免得后面读 `users` 的接口请求一直排队。失败时新版 admin 起不来、旧版照常服务；迁移每一步都先看还在不在，过一会儿重新发布就能接着做完。（如果凭据表已经删了、`users` 还没改完，旧版 admin 03:30 的清理和 04:00 的备份会失败，要在那之前重新发布。）`users` 那条 ALTER 放在最后，做完以后只剩写版本号；万一正好在这一步失败（库里已是新结构、版本还是旧的），旧版 admin 读用户就会出错，新版 admin 起不来时先看日志，是这种情况就马上重新发布 admin，迁移会把版本号补上。
- 删列以后 api、admin 都不能直接回退到迁移之前的版本：旧代码映射着已删的列；旧 admin 启动时也认不出新的迁移版本，`db-upgrade` 失败、起不来。要回退，先在新版 admin 里把库降回上一个版本，马上发布旧版 admin 和 api。旧版 admin 上来之前，新版 admin 如果重启，会按 `start.sh` 又升回去，那就再降一次。

## 五、安全和合规要求（agy 审阅后补充，Claude 已核对法条）

1. **网络日志留存不少于六个月（已实现，D-028）。** 《网络安全法》（2025 年修改，2026 年 1 月 1 日起施行）第二十三条第（三）项：网络运营者应当"采取监测、记录网络运行状态、网络安全事件的技术措施，并按照规定留存相关的网络日志不少于六个月"（[网信办公布的现行全文](https://www.cac.gov.cn/2025-12/29/c_1768735112911946.htm)，2026-09-28 核对）。云托管服务日志保存多久官方文档没写（2026-09-29 查）；接腾讯云日志服务 CLS 要另开服务、按量付费、多一个受托方，所以自建，不花钱，也不用创始人配置：
   - **记什么：** 每次请求（健康检查除外）一条：时间、服务、方法、接口路径（不含查询参数）、状态码、耗时、来源 IP、小程序用户编号（openid 用程序自己的密钥做 HMAC 后取前 16 位，去标识化；密钥第一次用到时随机生成，存在 `app_keys` 表）；核对台操作另记操作内容（做了什么、哪条记录、操作人）。口令错误、被拦下的、出错的请求也记。**不记**查询参数和请求、响应内容：检索词、企业名称、纠错内容都不进日志。uvicorn 自带的访问日志（带查询参数）已关掉；
   - **怎么存：** 请求处理完写进数据库暂存表 `access_logs`，同时打一行到容器标准输出（云托管日志里能实时查）；每天 0:30 `youju archive-logs` 把之前每天的归档到对象存储 `logs/access-日期.jsonl.gz`，上传成功才删暂存，再删掉 191–200 天前的归档，所以保存 190 天（多于六个月）。格式和备份一样是 gzip JSON Lines，最后一行写条数和 SHA-256。暂存表不进数据库备份，恢复备份也不动它；
   - **查某个用户的日志**（用户申请查阅、配合调查）：`youju log-uid <openid>` 算出编号，再在归档里找；
   - **出错时：** 写库失败不影响请求本身，提醒到群里（每个实例 10 分钟最多一条）；没写进去的记录先留在内存里（每个实例最多 5000 条），数据库恢复后下一次写库时一起补上（每条带随机编号，提交其实成功了却报错而补写第二次时，库里只留一条），实例在这期间重启才会丢（云托管日志里仍有）。归档按**写进库的时间**（数据库的时钟）分日，补写的记录归进补写那天的文件，不会覆盖已归档的文件，所以某天的文件里可能有前一天的请求，查的时候看记录里的 `at`。归档失败由 job.sh 提醒，暂存留着第二天再归档；暂存超过 190 天的直接删（在库里已经存满了期限）；
   - **没算在内的：** 定时任务的日志仍只在容器标准输出（失败都会提醒到群里）；是否也要保存六个月，请律师审阅时确认。隐私保护指引已按上面写明（记什么、不记什么、190 天、使用任何功能都会记录）。
2. **核对台开公网，口令要防猜（已实现）：** admin 服务启动时检查口令至少 32 位，不足不启动；口令输错限流：同一来源 10 分钟内错 5 次锁定（不设全局锁定，免得别人故意输错把管理员锁在外面；口令足够长，换来源地址也猜不中）；核对台每次操作（通过、驳回、标记变更、撤回，定类型，质检确认无误、退回待核对，来源试跑、接入，纠错标记处理）和每次口令错误都记审计日志（操作人、来源 IP、时间），纳入上一条的日志留存。按角色开放路径（白名单）：api 服务只开放小程序接口（`/api/v1/`）和健康检查，核对台、管理接口和早期样机的 `/api/documents` 等一律 404；admin 服务只开放核对台、管理接口和健康检查，外加经小程序云调用来的只读接口（要带平台注入的 `X-WX-SOURCE`，只开 GET）：10/12 起是首屏快照 `/api/v1/snapshot`（从公网直接访问和伪造这个请求头都验证过是 404），10/14 起加上首页、覆盖说明、搜索、日历、截止报表、名单报表、最近名单、查名单和文件详情（`ADMIN_READ_PATHS`），都不需要用户身份；导出、附件、我的、顾问、支付等要身份或按用户计次的接口仍只在 api 服务，admin 不信任身份头；公开接口只列可以公开的文件（来源是 1 级，或同一通知有 1 级来源的副本；2、3 级来源怎么展示接入前另行决定。10/13 Codex 审查：详情接口的 `url`、`original_urls` 和变更通知里新通知的标题还没按来源级别过滤，现在所有来源都是 1 级、不会带出，接入 2、3 级来源前要一起处理）；导出按用户限次数和并发（按请求计次，失败的请求也算一次）；来源级别只在创建时写（CSV 导入、来源接入都写 1 级），应用里没有修改级别的入口，要改只能直接改数据库——若以后加这个入口，要同时处理已有的订阅和发送时的并发（Codex 安全审查第 5 轮记录的前提）；线上两个服务都不开放接口文档（/docs、/openapi.json）。云托管能否限制公网访问来源（IP 白名单）**待核实**。
3. **数据库账号分开**（见第三节）。
4. **健康检查：** 两个服务都配置存活检查，地址 `/health`（检查数据库连接）；admin 服务还检查定时任务心跳——cron 每 5 分钟写一次，超过 15 分钟没更新就报不健康，由云托管重启容器，避免 cron 停了而每天的检查悄悄中断。

## 八、数据库（云托管 MySQL）

- **Serverless：** 算力按用量在 0.25–16 份之间自动伸缩（1 份约等于 1 核 2G）；10 分钟没有连接会自动暂停，暂停期间不收算力费，下次连接要等它恢复。代码连接时遇到"恢复中"会自动重试（`youju/db.py`）。

## 九、后台 AI（D-023）

- **用在哪：** 每轮定时任务里做类型判断和截止抽取（`youju ai-check`），和规则互相印证；名单解析时规则按表头找不到名称列的表格，请 AI 认出名称列（`youju parse-lists`，每个来源文件最多问 5 次）。核对台有"截止日期核对台"里的"AI 一致 / 仅 AI 找到 / 仅规则找到"标记，和单独的"类型待定"页（`/admin/kinds`）。
- **质检（AI 质检员）：** 每天 8 点复查已经发布给用户的截止日期。规则回查全部；配了 AI 时再抽查 20 份文件（同一条截止 30 天内不重复抽；每份文件发给 AI 的原文不超过 3000 字、一次最多 8 条，放不下的下次接着抽）。AI 说有误时要照抄原文里的那句话，这句话确实在原文里、也写着它说的日期才算存疑，对不上的只记下、不标。AI 出错的文件隔一天再试，连续 3 份出错就停，出错也提醒到群里。存疑的只标记、提醒到群里，不自动撤下；人在"质检存疑"页（`/admin/audit`）确认无误，或退回待核对：用户端立即不再显示（同一通知其他网址上的同一截止一起退回），候选回到核对台、标着"质检退回"和原因，必须有人重新核对——不会按同组已通过的自动沿用，也不会按导入的核对结果通过。
- **申报条件（D-052 第④项）：** 每轮 `youju extract-conditions` 抽条件，发给模型的是脱敏后的正文；模型给的每条都要带原文原句，服务端逐字核对（只容忍空白和全角半角差别），找不到的、句子里有脱敏信息的、条件里的数字原句里没有的、写成“能否申报”判断的都丢弃。留下的进 `/admin/conditions`：逐条通过、改写（原文引用不能改）或删除，整份确认后才对外，可撤回。详情页卡片叫“申报条件（已核对原文）”，不写怎么抽出来的，下方固定一行“条件以原文为准，不作为能否申报的判断”。正文变了（指纹对不上）立即不显示，按新正文重抽、重核。
- **红线不变：** 截止日期只有人工核对通过的才给用户看；类型不一致的由人定；名单只收通过机构名称规则的名称，状态仍按标题用词（D-018）。R1 不给用户看 AI 写的文字。
- **发给模型的数据：** 只有政府网站公开的通知标题、正文（入库时已脱敏）和名单表格样本，不含任何小程序用户的数据。表格发送前：表头像个人信息的整列不发，没有表头但多数值像人名的整列也不发，其余单元格脱敏（手机号、身份证、邮箱、银行账号、电话、联系人姓名）后截到 40 字，只发前 10 行。
- **依据：** 《个人信息保护法》第二十七条（在合理范围内处理已合法公开的个人信息）、第二十一条（委托处理要约定目的、方式、保护措施等并监督受托人），2026-09-28 在全国人大网原文核对（agy 提出、Claude 核实）。
- **上线前要做：** 开通百炼时看清阿里云的服务协议和数据处理条款（调用数据是否会用于模型训练、保存多久），控制台里有关闭数据用于训练的选项就关掉（agy 提出，待开通时核实有没有这个选项）；留存所用模型的备案信息备查；隐私保护指引不涉及用户数据，可以不改，请律师审阅协议时一并确认。
- **来源接入（来源接入 Agent）：** 后台"来源接入"页（`/admin/sources`）输入政府网站栏目网址（只收 .gov.cn）点"试跑"：按 robots 礼貌地抓一次列表页（同一网站 10 秒内只试跑一次），用通用规则识别条目；配了 AI 时 AI 给登记建议（层级、省份、部门简称、部门全称、栏目名；部门全称和栏目名只有网页里写着的才填），通用规则认不出（或勾选"也让 AI 写抓取规则"）时 AI 写 CSS 选择器、在同一页面试跑，识别出至少 3 条带日期的条目才给人看。人核对条目和登记信息后点"确认接入"，来源直接写进数据库（D-025），下一轮定时抓取开始检查，第一次抓到的条目算基线。命令行 `youju try-source <网址>` 只试跑、不写库。发给 AI 的只有这张政府网页本身。
- **纠错分诊：** 每轮定时任务对还没处理、有对应文件的纠错做一次：规则回查这份文件全部已发布的截止，配了 AI 时再请 AI 对照原文复查（不看 30 天内抽查过没有；和质检员同一套判断，要照抄原文句子、写着它给出的日期才算存疑）。结果写在纠错旁边，例如"已发布的截止 2 条，规则和 AI 复查 1 条存疑……；还有 1 条截止候选待核对"；AI 判的类型和页面显示的不一样时也提一句。存疑的进"质检存疑"由人复核，人确认过无误的不再标。**用户写的纠错内容不发给 AI，分诊时也不读。** AI 出错的下一轮再试。
- **运维日报：** 数字都是查数据库算的，待办条数和核对台一致。AI 只从候选截止还没过的待核对通知里（按候选日期最近的 30 份，只给编号、发文单位、标题和候选日期）挑 3 份建议先核对，编号必须在给它的清单里，理由只在群里给内部看。群消息有 1800 字节上限，放不下时先少列 AI 建议，数字不截。
- **费用：** 百炼多数千问型号新开通各送 100 万 tokens（90 天，北京地域）；之后 qwen-flash 每百万 tokens 输入 0.15 元、输出 1.5 元（2026-09-28 官方价格页）。每轮最多检查 300 份文件。每条用到 AI 的命令结束时把用量记到 `ai_usage` 表（按北京时间的天、任务、模型累加调用次数、出错次数和 tokens），运维日报据此报昨天的用量、估算费用和各模型累计用量；本机跑评测脚本的用量不在云上的台账里。
- **AI 结果的内容安全（门槛第 4 道，10/28）：** admin 处理 AI 解读、条款对照时，结果存进去之前先查两层：
  - 本地高危词库（`safety_words`，词库在 `src/youju/data/safety_words.json`），一句一句查；
  - 经开放接口服务调微信 `wxa/msg_sec_check`（2.0，带提交任务的人的 openid）。纠错一直用这个接口，它属于"微信令牌权限配置"里和订阅消息放在一起的那一组。
  - 查的是显示给用户的原句。通过的结果记上标记（词库版本、查没查微信），读的时候没有标记的不显示，线上标记里没写着查过微信的（admin 配错、没认出在云托管里）也不显示；词库升版以后，读的时候先用本地词库再查一遍，每天 03:30 的清理把命中的撤下。
  - 没通过的不显示、退回次数，记一条处置记录（`ai_safety_hits`，190 天，不记用户编号、不存结果文字），同一份内容 1 天内不再调模型和微信。
  - 接口出错不放行：暂时性的错误原地重试（最多查 3 次），还不行任务直接失败、退回次数（`AI_CHECK_DOWN`），不重排，免得重新调模型。每次出错写一行运行日志"AI 结果内容安全检测出错：任务 N，第 k 次，errcode X"，并往运维群提醒（按库里记的时间，每小时最多一条；单个用户两小时内没访问过小程序的 61010 不提醒）。运维日报的"内容安全（24 小时）"一行报拦下几次、出错几个、新抓的正文和附件命中词库几份。
  - **发布 admin 以后要实测：** 用白名单账号提交一份解读，结果正常出来，运行日志里没有上面那行"检测出错"。还可以在 admin 容器里跑 `youju safety-probe --openid <你的 openid>`（先打开一次小程序），抽 30 份 AI 会显示的原句（最近做完的结果，不够再从最近的通知里取像申报要点的段落）过微信检查，看有多少被判成 review、risky。这一步只读，只打印份数和编号；每份占一次当天的次数。
  - **admin 调不通时每个 AI 任务都会失败（不放行）：**
    - **先把 AI 退回白名单或关掉**：两个服务一起删掉 `YOUJU_AI_ADVISOR_AUDIENCE` 那一行，或者把 `YOUJU_AI_ADVISOR_ENABLED` 改成 false。然后查原因：请创始人在"微信令牌权限配置"里确认登记了 `wxa/msg_sec_check`、"开放接口服务"开着，再重新发布。
    - **不要只回退 admin：** 新的 api 不显示没有检查标记的结果，旧 admin 生成的结果都没有标记，只回退 admin 等于 AI 全坏。要回退就 admin、api 一起回退（迁移 0042 只加一张表，回退是安全的）。
    - **回退只换代码，不降库：** 两个服务一起退回旧代码就行，不要跑 `alembic downgrade` 退到 0042 以前——那会删掉 `ai_safety_hits` 表，处置记录要留 190 天。
  - **小程序正式发布（上架）以前，这个接口每天最多调 100 次：** 一份结果一般查一次，原句加起来超过 2500 字的分几次查，复用缓存的结果也查；纠错也占这个数。提审当天不要在线上大量实测，免得把当天的次数用完、审核员用的时候报"内容安全检测暂时不可用"。

## 六、冷启动和首屏快照（10/12）

- **现象**：接口服务（api）最小 0 个实例，空闲约 25 分钟后缩到 0；10/12 实测再打开要 67 秒才第一次取到数据（程序本身启动不到 1 秒，主要是平台拉起实例）。数据库不是原因：admin 每分钟跑的工具任务会连数据库，Serverless MySQL 一直不暂停。
- **根治**是把 api 最小实例设为 1（约 21–86 元/月，看规格），创始人 10/12 决定不加。
- **免费的缓解**（#217–#220）：小程序读数据的请求冷启动时最多等 90 秒；首页、截止页默认视图、查名单先显示手机上存的上次数据；同时向常驻的 admin 要首屏快照 `GET /api/v1/snapshot`（首页、截止页默认视图、最近名单和名单统计，和各接口内容一致，不带用户数据，按日期缓存 60 秒），几秒内就是最新数据，接口服务醒了再换成实时的。
- ~~搜索结果、通知详情、我的客户仍直接用 api，冷启动时最多等一分钟左右，期间显示"正在连接，比平时慢一点"。~~ 10/14 起也先走 admin，见下一条。

- **10/14 加一层（创始人同意）**：当天实测接口服务空闲一整天后 3–5 分钟才恢复（10/12 测的是空闲 25 分钟后 67 秒）。小程序不需要身份的只读请求（首页、搜索、详情、截止、日历、名单、查名单、覆盖说明）改为先发给常驻的 admin（8 秒没回就放弃），admin 拦下、出错、调用失败或超时时这一次改发接口服务，再按冷启动规则重试；接口自己的答复（如"该文件已下架"、422、429）直接显示。导出、打开附件仍走接口服务，冷启动时照旧要等。代价：admin 只有一个实例、还要跑抓取，用户多了会变慢，到时再看要不要给 api 开最小实例。
- **10/15 打开登录后（D-067）**：同意协议、关注、纠错、删除、导出都要用接口服务；写操作不自动重试（怕重复提交），以前冷启动时会直接报"网络不太好"（当天实测"我的"页面约 2 分钟才拿到登录状态）。小程序改为：写操作前，接口服务 20 分钟内没答复过，就先发 `GET /health`（不要身份、不记网络日志）叫醒它，按读数据的冷启动规则重试，90 秒为限，期间显示"正在连接…"；答复了再提交，叫不醒就不提交、请用户过一分钟再试。打开小程序和回到前台时也悄悄叫一次（预热，不显示提示），用户多半先看内容，点按钮时它已经醒了；提交时赶上正在进行的预热就跟着等，并从这时起再给足 90 秒。"我的"、关注、我的数据、关注的新文件四页加载慢时显示"正在连接，比平时慢一点"。代价：有人打开小程序时接口服务就会起来，按量计费会比只在登录操作时多一点，最多和常驻 1 个实例差不多。空闲一整天后要 3–5 分钟才起来的情况仍会超过 90 秒，根治是最小实例 1，等创始人定。
