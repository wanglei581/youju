# 部署：微信云托管 + 云托管自带 MySQL（#32 草案）

> 状态：草案。镜像还没有构建验证过（本机没有 Docker），开通云托管后第一次构建时验证，结果补在本文。
> 依据：微信官方文档（2026-09-28 本机直接访问核对），链接见文中。
> 数据库：创始人决定先用免费的（D-022），用云托管自带的 MySQL 8.0，不另买腾讯云 PostgreSQL。

## 一、结构

| 服务 | 用途 | 公网 | 实例数 | 环境变量 `YOUJU_ROLE` |
|---|---|---|---|---|
| 小程序接口 | 小程序全部接口（`/api/v1/*`） | **关闭** | 按量伸缩，最小 0、**最大 3**（导出按实例限次数和并发，实例数有上限才封得住资源用量；首批试用足够，用户多了再调） | `api` |
| 核对台和定时任务 | 截止日期核对台、管理接口；每天定时检查栏目、补详情、抽截止、解析名单 | 开启（只挂核对台和管理接口，用口令） | **固定 1 个** | `admin` |

两个服务用同一个镜像（仓库根目录 `Dockerfile`）。

- **为什么小程序接口关闭公网：** 小程序用 `wx.cloud.callContainer` 调用时，服务收到的请求头自动带用户身份（`X-WX-OPENID` 等），官方建议只有小程序调用的服务关闭公网访问，并用 `X-WX-SOURCE` 判断来源（[容器内变量信息](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/development/weixin/index)、[调用云托管服务](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/development/call/mini.html)）。关闭公网后，别人无法伪造用户身份头。
- **为什么定时任务服务固定 1 个实例：** 云托管没有单独的定时触发器，官方做法是在容器里跑 cron（[定时触发](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/practice/trigger.html)）。多个实例会各跑一遍，缩到 0 个实例则不跑，所以固定 1 个。
- **限制：** `callContainer` 请求不超过 100 KiB、返回不超过 1000 KiB（导出文件要控制在这以内）；小程序基础库最低 2.23.0。

## 二、定时任务（北京时间）

| 时间 | 命令 | 作用 |
|---|---|---|
| 06:30、11:30、15:30、20:30 | `round.sh`（每天 4 轮，按顺序执行下面步骤；整轮加锁，上一轮还没跑完就跳过这一轮并提醒） | |
| ① | `youju crawl` | 检查全部启用栏目，发现新文件 |
| ② | `youju check-sources` | 抓取成功后才运行：核对今天（北京时间零点起）各启用栏目的最近一次检查，成功率低于 95% 或有漏检就发提醒 |
| ③ | `youju fetch-details --limit 300 --workers 4` | 补抓详情（正文、机关、文号、附件） |
| ④ | `youju extract-deadlines` | 从正文抽截止候选，进入核对台 |
| ④+1 | `youju extract-fields` | 从申报通知正文抽支持方式和申报对象候选，进入字段核对台 |
| ④+ | `youju ai-check --limit 300` | AI 做类型判断和截止抽取，和规则互相印证：规则候选标"AI 一致 / 仅规则找到"，AI 新找到的作为"仅 AI 找到"送进核对台（都要人工核对）。没配 AI 密钥时跳过 |
| ④++ | `youju triage-feedback` | 纠错分诊：用户纠错过、还没处理的文件，用规则和 AI 复查已发布的截止日期，结果写在"纠错与申请覆盖"页的纠错旁边；存疑的进"质检存疑"。纠错内容不发给 AI |
| ⑤ | `youju parse-lists` | 解析名单附件（单次最多 200 个附件） |
| ⑥ 只在 06:30 那一轮 | `youju notify` | 这一轮全部做完后发微信订阅提醒（截止前 3 天、关注有新文件），每天一次 |
| 00:30 | `youju archive-logs` | 访问日志归档：把之前每天（北京时间）的访问日志归档到对象存储 `logs/access-日期.jsonl.gz`，上传成功才删暂存；删掉 191–200 天前的归档，所以保存 190 天；失败发提醒（见第五节第 1 条） |
| 03:30 | `youju cleanup` | 按保存期限删除过期的个人信息（纠错、提醒授权、埋点） |
| 04:00 | `youju backup` | 数据库备份：整库导出（同一时刻的数据），上传到云托管对象存储 `backups/youju-日期.jsonl.gz`，删掉 31–40 天前的；失败发提醒（见第八节） |
| 08:00 | `youju audit-deadlines --sample 20` | 质检已发布的截止日期：规则回查全部（早于发布日期、正文缺失、正文里找不到这个日期），配了 AI 时再抽查 20 份；存疑的和 AI 出错的提醒到群里，在核对台"质检存疑"页复核（确认无误或退回待核对） |
| 08:00 质检做完后 | `youju daily-report` | 运维日报发到群里：今天栏目检查、24 小时新文件和补详情、新截止候选、核对进度和待办（待核对、30 天内截止、类型待定、质检存疑、纠错）、用户总数、昨天的 AI 用量和费用；配了 AI 时附上 AI 建议先核对的 3 份通知。`--dry-run` 只打印不发 |

抓取规则不变：YoujuBot 标识、遵守 robots、每站 3 秒、遇拦截即停。同一任务不重叠（上一次没跑完就跳过这次并提醒），单次最长 3 小时，超时算失败并提醒。任务日志打到容器标准输出，在云托管"服务日志"里看。提醒渠道待创始人确定；配置企业微信群机器人后，可用 `youju alert "测试文本"` 验证。`check-sources` 已发送详细提醒时，任务包装器不再重复发送通用失败提醒。

数据库迁移只在 admin 服务启动时执行，并用 MySQL 命名锁（`GET_LOCK`）：滚动发布时即使新旧两个实例同时启动，也只有一个在迁移。

## 三、环境变量

| 变量 | 服务 | 说明 |
|---|---|---|
| `YOUJU_ROLE` | 两个 | `api` 或 `admin` |
| `YOUJU_ADVISOR_ENABLED` | 两个 | `false`（默认）；顾问技能包验收完成并获批准后才设为 `true` |
| `YOUJU_DATABASE_URL` | 两个 | 云托管 MySQL 的内网地址（控制台 MySQL 页"网络信息"），形如 `mysql+pymysql://账号:密码@内网地址:3306/youju?charset=utf8mb4`；admin 用 `youju_admin`，api 用 `youju_api`。**由创始人在云托管控制台填写，不要发给任何人** |
| `YOUJU_ADMIN_TOKEN` | admin | 核对台口令；由创始人设定，只在控制台填写；至少 32 位随机字符 |
| `YOUJU_ALERT_WEBHOOK` | admin | 可空；企业微信群机器人地址，由创始人仅在云托管控制台填写，不要发给任何人，也不要写入日志 |
| `YOUJU_TRUST_WX_HEADERS` | api | 填 `true`：用户身份只取云托管注入的 `X-WX-OPENID`（且要有 `X-WX-SOURCE`）。api 服务不填不启动 |
| `YOUJU_DEV_OPENID` | 都不填 | 本机开发用的固定身份；线上两个服务填了不启动（否则所有请求都会被当成同一个用户） |
| `YOUJU_SEND_WX_MESSAGES` | admin | 填 `true` 时定时任务真正发送订阅消息（经云托管开放接口服务）；不填只演练、不发送 |
| `YOUJU_AI_API_KEY` | admin | 阿里云百炼的 API Key（北京地域）；**由创始人在云托管控制台填写，不要发给任何人**。不填就不调用 AI，照常用规则 |
| `YOUJU_EXPORTS_PER_10MIN` | api | 可不填，默认 30：每个用户 10 分钟内最多导出几次（每个实例另外同时最多生成 4 份）。做验收 C2"连续导出 100 次"时临时调高，做完改回 |
| `YOUJU_CLOUD_ENV` | admin | 云托管环境 ID（控制台首页可见，形如 `prod-xxxx`）：每天的数据库备份存到这个环境的对象存储（验收 A6）。不填时备份任务失败并提醒 |
| `YOUJU_AI_MODEL`、`YOUJU_AI_BASE_URL` | admin | 可不填：默认 `qwen-flash`、`https://dashscope.aliyuncs.com/compatible-mode/v1` |
| `YOUJU_TEMPLATE_DEADLINE`、`YOUJU_TEMPLATE_NEWDOCS` | 两个 | 订阅消息模板（JSON：模板 ID 和字段对应）。创始人在小程序后台选定模板后，由 Claude 按模板字段生成 |

**数据库账号分开（最小权限）：** 建库和建账号的语句在 `backend/deploy/mysql_accounts.sql`。admin 服务用 `youju_admin`（可建表迁移、写入抓取数据）；api 服务用 `youju_api`（能读全部表，只能写用户、关注、订阅、纠错、埋点这 5 张表；访问日志和访问日志的密钥只能新增，不能改、删）。云托管 MySQL 最多 3 个账号，正好是 root 加这两个。本机验证过：`youju_api` 删内容表、建表都会被拒绝。注意这是**按表**的权限：`youju_api` 能写这 5 张表里任何用户的行，只能写自己的数据由代码保证（每个写入都按当前用户过滤，有测试覆盖）；分开账号的作用是即使接口出问题，也改不了政府文件、截止日期这些内容表，更删不了表。

## 四、首次部署步骤

**创始人（需要实名和付费）：**
1. 开通微信云托管（[控制台](https://cloud.weixin.qq.com/cloudrun)，微信扫码），创建环境：环境名 `prod`，服务名 `admin`。第一个环境有 3 个月免费额度，删掉后不再有，不要建了又删。
2. 开通 MySQL：控制台 → MySQL → 开通，版本选 **8.0**（开通后不能改）。设一个 root 密码，自己保管。8.0 开通时要选表名是否区分大小写，选默认即可（我们的表名都是小写）。同一环境里的服务和数据库天然内网互通，不用另配网络。
3. 在 MySQL 页"数据库管理"用 root 登录，执行 `backend/deploy/mysql_accounts.sql` 的第①部分（建库、建 `youju_admin`）。
4. 生成 CLI 密钥（控制台 → 设置 → CLI 密钥，管理员扫码），在自己电脑的终端运行 `wxcloud login -a <AppID>`，按提示粘贴密钥。之后由 Claude 用命令行部署。
5. 在 `admin` 服务里填上面的环境变量（密码、口令这类只由创始人填）。
6. 备份用的设置（验收 A6）：
   - 控制台 → 云调用 → 微信令牌权限配置：登记 `/tcb/uploadfile`、`/tcb/batchdeletefile`、`/tcb/batchdownloadfile`（和发送订阅消息、内容安全检查的接口放在一起），再打开"开放接口服务"开关。开关打开前已有的服务版本要重新发布才生效；
   - 对象存储 → 权限设置：选"所有用户不可读（只有管理员可读写）"。备份里有用户数据，和数据库同等对待；

   - 核对台（admin 服务）开着公网，指南建议减少被攻击时的损失：实例副本数最大值调小（admin 本来就固定 1 个）；云托管"告警设置"里加"调用次数"和"平均实例个数"两项告警，阈值取正常运行时的 2–5 倍（上线跑几天、看过正常值后再设）；腾讯云侧设余额预警，余额快速减少时提醒。

## 五、安全和合规要求（agy 审阅后补充，Claude 已核对法条）

1. **网络日志留存不少于六个月（已实现，D-028）。** 《网络安全法》（2025 年修改，2026 年 1 月 1 日起施行）第二十三条第（三）项：网络运营者应当"采取监测、记录网络运行状态、网络安全事件的技术措施，并按照规定留存相关的网络日志不少于六个月"（[网信办公布的现行全文](https://www.cac.gov.cn/2025-12/29/c_1768735112911946.htm)，2026-09-28 核对）。云托管服务日志保存多久官方文档没写（2026-09-29 查）；接腾讯云日志服务 CLS 要另开服务、按量付费、多一个受托方，所以自建，不花钱，也不用创始人配置：
   - **记什么：** 每次请求（健康检查除外）一条：时间、服务、方法、接口路径（不含查询参数）、状态码、耗时、来源 IP、小程序用户编号（openid 用程序自己的密钥做 HMAC 后取前 16 位，去标识化；密钥第一次用到时随机生成，存在 `app_keys` 表）；核对台操作另记操作内容（做了什么、哪条记录、操作人）。口令错误、被拦下的、出错的请求也记。**不记**查询参数和请求、响应内容：检索词、企业名称、纠错内容都不进日志。uvicorn 自带的访问日志（带查询参数）已关掉；
   - **怎么存：** 请求处理完写进数据库暂存表 `access_logs`，同时打一行到容器标准输出（云托管日志里能实时查）；每天 0:30 `youju archive-logs` 把之前每天的归档到对象存储 `logs/access-日期.jsonl.gz`，上传成功才删暂存，再删掉 191–200 天前的归档，所以保存 190 天（多于六个月）。格式和备份一样是 gzip JSON Lines，最后一行写条数和 SHA-256。暂存表不进数据库备份，恢复备份也不动它；
   - **查某个用户的日志**（用户申请查阅、配合调查）：`youju log-uid <openid>` 算出编号，再在归档里找；
   - **出错时：** 写库失败不影响请求本身，提醒到群里（每个实例 10 分钟最多一条）；没写进去的记录先留在内存里（每个实例最多 5000 条），数据库恢复后下一次写库时一起补上（每条带随机编号，提交其实成功了却报错而补写第二次时，库里只留一条），实例在这期间重启才会丢（云托管日志里仍有）。归档按**写进库的时间**（数据库的时钟）分日，补写的记录归进补写那天的文件，不会覆盖已归档的文件，所以某天的文件里可能有前一天的请求，查的时候看记录里的 `at`。归档失败由 job.sh 提醒，暂存留着第二天再归档；暂存超过 190 天的直接删（在库里已经存满了期限）；
   - **没算在内的：** 定时任务的日志仍只在容器标准输出（失败都会提醒到群里）；是否也要保存六个月，请律师审阅时确认。隐私保护指引已按上面写明（记什么、不记什么、190 天、使用任何功能都会记录）。
2. **核对台开公网，口令要防猜（已实现）：** admin 服务启动时检查口令至少 32 位，不足不启动；口令输错限流：同一来源 10 分钟内错 5 次锁定（不设全局锁定，免得别人故意输错把管理员锁在外面；口令足够长，换来源地址也猜不中）；核对台每次操作（通过、驳回、标记变更、撤回，定类型，质检确认无误、退回待核对，来源试跑、接入，纠错标记处理）和每次口令错误都记审计日志（操作人、来源 IP、时间），纳入上一条的日志留存。按角色开放路径（白名单）：api 服务只开放小程序接口（`/api/v1/`）和健康检查，核对台、管理接口和早期样机的 `/api/documents` 等一律 404；admin 服务只开放核对台、管理接口和健康检查；公开接口只列可以公开的文件（来源是 1 级，或同一通知有 1 级来源的副本；2、3 级来源怎么展示接入前另行决定）；导出按用户限次数和并发（按请求计次，失败的请求也算一次）；来源级别只在创建时写（CSV 导入、来源接入都写 1 级），应用里没有修改级别的入口，要改只能直接改数据库——若以后加这个入口，要同时处理已有的订阅和发送时的并发（Codex 安全审查第 5 轮记录的前提）；线上两个服务都不开放接口文档（/docs、/openapi.json）。云托管能否限制公网访问来源（IP 白名单）**待核实**。
3. **数据库账号分开**（见第三节）。
4. **健康检查：** 两个服务都配置存活检查，地址 `/health`（检查数据库连接）；admin 服务还检查定时任务心跳——cron 每 5 分钟写一次，超过 15 分钟没更新就报不健康，由云托管重启容器，避免 cron 停了而每天的检查悄悄中断。
5. **名单里的个人信息：** 已处理——名单解析只取企业和机构名称列，表头是姓名、联系人、电话、身份证等的列一律丢弃；招聘、职称、考试合格人员等个人名单不解析（#45、#44）。
6. **抓取不访问内网（已实现）：** 每次连接前检查域名解析出的地址，内网、本机、云服务器元数据（169.254.169.254）等非公网地址一律不连；页面跳转、robots.txt 跳转同样逐跳检查。连接直接固定到检查过的地址（证书仍按原域名校验），检查之后 DNS 结果被改动也连不到内网；收到响应后再核对一次实际连上的地址。抓取直连，不走环境变量里的代理，也不复用连接。防止某个政府网站的域名或跳转指向云托管内部服务。
7. **线上只认平台注入的身份（已实现）：** 见第三节 `YOUJU_TRUST_WX_HEADERS`、`YOUJU_DEV_OPENID`，配错服务不启动（admin 服务开公网，设了 `YOUJU_TRUST_WX_HEADERS` 也不启动）。api 服务必须关闭公网访问：只有经 `callContainer` 进来的请求，身份由平台填写；公网请求里的这些请求头可能是请求方自己带的。

## 八、数据库（云托管 MySQL）

- **Serverless：** 算力按用量在 0.25–16 份之间自动伸缩（1 份约等于 1 核 2G）；10 分钟没有连接会自动暂停，暂停期间不收算力费，下次连接要等它恢复。代码连接时遇到"恢复中"会自动重试（`youju/db.py`）。
- **实际不会暂停：** 两个服务的健康检查都要查一下数据库（`/health` 会执行 `select 1`），所以数据库会一直按最低 0.25 份算力计费。头 3 个月在免费额度内（720 份·小时，0.25 份全天运行 90 天约 540），之后约 62 元/月（0.342 元/份·小时）。如果要省这部分，可以让健康检查不查数据库，代价是早上第一个请求要等数据库恢复几秒。
- **搜索速度（验收 C1）：** 按类型筛选原来把标题规则翻译成 800 多个模糊匹配条件逐行算，换成 MySQL 后在 1.7 万份文件上实测要 2 秒（超过 1.5 秒的上限）。现在入库时按标题规则算好类型存在 `documents.rule_kind`，筛选只比较这一列；规则随版本更新，admin 服务每次启动时在迁移之后跑 `youju reclassify` 重算（1.7 万份几秒钟），还没算的当场按规则判断，结果一样。9/29 本机测速（1.7 万份文件、20 万条名单，服务端处理时间中位数）：首页 37 ms，各种搜索 13–150 ms，详情 5 ms，日历 8 ms，查名单约 245 ms。测速方法：`backend/scripts/bench_api.py`，在专门的测速库上跑；上线后在线上环境再测一次（含网络）。加了访问日志（每次请求写一条，D-028）后 9/29 下午复测，开、关日志各跑 30 次：首页都是 25 ms，详情 4→5 ms，其余在误差以内，每次请求约多 1 毫秒。（同一天中午机器负载 24 时测过一次，各项慢了几倍、开关日志都一样，那次不作数。）
- **本机开发：** `backend/scripts/dev_mysql.sh start` 启动项目内的 MySQL 8.0（端口 33306，root 无密码，只监听本机）。
- **写法约定：** 时间一律按 UTC 存（`DATETIME(6)`，见 `youju/dbtypes.py`）；正文用 `MEDIUMTEXT`（开发库最长的正文约 40 万字节，超过 `TEXT` 的 64KB）；事务隔离用"读已提交"；网址类字段参与唯一索引，所以有长度上限（文件网址 512 字，名单来源网址 400 字，超长的跳过并记日志）。
- **备份（验收 A6）：** 云托管 MySQL 没有自带备份，由 admin 服务每天凌晨 4 点做（`youju backup`）：
  - 所有表在同一个"可重复读"事务里导出，是同一时刻的数据；格式是 gzip 压缩的 JSON Lines（第一行写格式版本、迁移版本、导出时间和各表条数，最后一行写各表内容的 SHA-256，没有这一行就是文件不完整），和数据库品牌、版本无关；
  - 经"开放接口服务"（免 access_token）上传到云托管对象存储 `backups/youju-日期.jsonl.gz`（北京时间日期，同一天重跑就覆盖），再删掉 31–40 天前的，所以保留 30 天；接口参数按官方文档"获取文件上传链接""删除文件"（2026-09-28 核对）；
  - 恢复用 `youju restore <文件>`：目标库要已用同一版本的代码迁移好、而且是空的。先锁住全部表（恢复期间定时任务写不进来），逐行校验字段后写入，在同一个事务里核对各表条数、外键和内容的 SHA-256，全部对上才提交；任何一步不对就回滚，目标库保持原样；
  - **恢复要用生成备份时的代码版本：** 备份文件第一行写着迁移版本，恢复命令按当前代码的表结构逐行核对字段，版本不同会拒绝（9/29 实测）。所以恢复旧备份时，先用那个版本的代码（按迁移版本找对应的发布版本或镜像）把空库迁移到同一版本并恢复，再换回新版本迁移；平时每天用当前版本备份，出事用当前版本恢复，不受影响；
  - 上传遇到网络中断、服务繁忙会等 5 秒、15 秒各重试一次；没开通、没登记接口这类错误不重试，直接失败提醒；
  - 不备份访问日志暂存表 `access_logs`（它每天归档，归档另存 190 天，见第五节第 1 条），恢复也不动它；
  - 备份里有用户数据：存储桶权限设为"所有用户不可读（只有管理员可读写）"；隐私保护指引已写明备份保留 30 天、注销后备份中的副本在 30 天内随备份删除，律师审阅时一并确认；
  - **本机演练（9/28–9/29）：** 用本机核对台的库（16 张表、20.4 万条记录）备份，压缩后 7.5 MB，用时约 5 秒；恢复到新建的空库并做完全部核对用时 12 秒。另用 MySQL 表校验和（`CHECKSUM TABLE`）逐表比对，也全部相同；
  - 容器的系统时区设为北京时间（`/etc/localtime`），cron 按北京时间排定时任务；CI 检查容器里 `date +%z` 是 `+0800`。

## 九、后台 AI（D-023）

- **用在哪：** 每轮定时任务里做类型判断和截止抽取（`youju ai-check`），和规则互相印证；名单解析时规则按表头找不到名称列的表格，请 AI 认出名称列（`youju parse-lists`，每个来源文件最多问 5 次）。核对台有"截止日期核对台"里的"AI 一致 / 仅 AI 找到 / 仅规则找到"标记，和单独的"类型待定"页（`/admin/kinds`）。
- **质检（AI 质检员）：** 每天 8 点复查已经发布给用户的截止日期。规则回查全部；配了 AI 时再抽查 20 份文件（同一条截止 30 天内不重复抽；每份文件发给 AI 的原文不超过 3000 字、一次最多 8 条，放不下的下次接着抽）。AI 说有误时要照抄原文里的那句话，这句话确实在原文里、也写着它说的日期才算存疑，对不上的只记下、不标。AI 出错的文件隔一天再试，连续 3 份出错就停，出错也提醒到群里。存疑的只标记、提醒到群里，不自动撤下；人在"质检存疑"页（`/admin/audit`）确认无误，或退回待核对：用户端立即不再显示（同一通知其他网址上的同一截止一起退回），候选回到核对台、标着"质检退回"和原因，必须有人重新核对——不会按同组已通过的自动沿用，也不会按导入的核对结果通过。
- **红线不变：** 截止日期只有人工核对通过的才给用户看；类型不一致的由人定；名单只收通过机构名称规则的名称，状态仍按标题用词（D-018）。R1 不给用户看 AI 写的文字。
- **发给模型的数据：** 只有政府网站公开的通知标题、正文（入库时已脱敏）和名单表格样本，不含任何小程序用户的数据。表格发送前：表头像个人信息的整列不发，没有表头但多数值像人名的整列也不发，其余单元格脱敏（手机号、身份证、邮箱、银行账号、电话、联系人姓名）后截到 40 字，只发前 10 行。
- **依据：** 《个人信息保护法》第二十七条（在合理范围内处理已合法公开的个人信息）、第二十一条（委托处理要约定目的、方式、保护措施等并监督受托人），2026-09-28 在全国人大网原文核对（agy 提出、Claude 核实）。
- **上线前要做：** 开通百炼时看清阿里云的服务协议和数据处理条款（调用数据是否会用于模型训练、保存多久），控制台里有关闭数据用于训练的选项就关掉（agy 提出，待开通时核实有没有这个选项）；留存所用模型的备案信息备查；隐私保护指引不涉及用户数据，可以不改，请律师审阅协议时一并确认。
- **来源接入（来源接入 Agent）：** 后台"来源接入"页（`/admin/sources`）输入政府网站栏目网址（只收 .gov.cn）点"试跑"：按 robots 礼貌地抓一次列表页（同一网站 10 秒内只试跑一次），用通用规则识别条目；配了 AI 时 AI 给登记建议（层级、省份、部门简称、部门全称、栏目名；部门全称和栏目名只有网页里写着的才填），通用规则认不出（或勾选"也让 AI 写抓取规则"）时 AI 写 CSS 选择器、在同一页面试跑，识别出至少 3 条带日期的条目才给人看。人核对条目和登记信息后点"确认接入"，来源直接写进数据库（D-025），下一轮定时抓取开始检查，第一次抓到的条目算基线。命令行 `youju try-source <网址>` 只试跑、不写库。发给 AI 的只有这张政府网页本身。
- **纠错分诊：** 每轮定时任务对还没处理、有对应文件的纠错做一次：规则回查这份文件全部已发布的截止，配了 AI 时再请 AI 对照原文复查（不看 30 天内抽查过没有；和质检员同一套判断，要照抄原文句子、写着它给出的日期才算存疑）。结果写在纠错旁边，例如"已发布的截止 2 条，规则和 AI 复查 1 条存疑……；还有 1 条截止候选待核对"；AI 判的类型和页面显示的不一样时也提一句。存疑的进"质检存疑"由人复核，人确认过无误的不再标。**用户写的纠错内容不发给 AI，分诊时也不读。** AI 出错的下一轮再试。
- **运维日报：** 数字都是查数据库算的，待办条数和核对台一致。AI 只从候选截止还没过的待核对通知里（按候选日期最近的 30 份，只给编号、发文单位、标题和候选日期）挑 3 份建议先核对，编号必须在给它的清单里，理由只在群里给内部看。群消息有 1800 字节上限，放不下时先少列 AI 建议，数字不截。
- **费用：** 百炼多数千问型号新开通各送 100 万 tokens（90 天，北京地域）；之后 qwen-flash 每百万 tokens 输入 0.15 元、输出 1.5 元（2026-09-28 官方价格页）。每轮最多检查 300 份文件。每条用到 AI 的命令结束时把用量记到 `ai_usage` 表（按北京时间的天、任务、模型累加调用次数、出错次数和 tokens），运维日报据此报昨天的用量、估算费用和各模型累计用量；本机跑评测脚本的用量不在云上的台账里。
