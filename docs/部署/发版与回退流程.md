# 发版与回退流程（2026-10-19）

> 差距清单 R1、R2、R3。写给创始人和团队：每次发版照这一页走，出问题照最后两节回退。
> 生产部署、提审、发布都要创始人在聊天里同意（[部署要同意](../开发流程.md)）；团队准备命令和核对步骤，不绕过。

## 一、发版前（团队做）

1. **同一个提交**：要发的提交已经合进 main，在 GitHub 上 CI 全绿（后端、小程序、发布工具三组）；记下完整 SHA。
2. **看有没有迁移**：`git diff <线上SHA> <新SHA> -- backend/alembic/versions`。
   - 有迁移：先发 admin（启动时迁移），再发 api。删表、删列的迁移反过来：先发 api（新代码不再用这些列），api 全量、旧版本归零后再发 admin。
   - 每个迁移写清楚"回退时怎么办"（见第五节）。
3. **新旧小程序都要能用**：后端是一次全量切换，而小程序正式版用户手机上可能还是旧版本（尤其分阶段发布期间）。接口只加不改；要改返回格式或协议版本时，先确认旧版小程序收到后会提示更新，而不是报错。
4. **演练**：`backend/deploy/cloud_deploy.sh <环境ID> <admin|api> <SHA> --dry-run`，看上传的文件清单和大小。演练也会做第二节说的发布前核对，核对不过的这时就能看到。
5. **把要做的事写成一张单子发给创始人**：SHA、包含哪些 PR、迁移、要执行的命令（如 `youju cleanup`）、要不要换体验版、怎么判断成功、出问题怎么回退。

## 二、后端发布（创始人在聊天里同意后，团队在这台电脑上执行）

发布、回退的命令都由团队在这台电脑上执行（`wxcloud` 已登录）；创始人不用敲命令，只在聊天里同意。

平常的顺序是**先 admin（启动时迁移数据库），再 api**；这次有删表、删列的迁移时反过来（见第一节第 2 条）。

```sh
backend/deploy/cloud_deploy.sh <环境ID> admin <SHA>
```

等 admin 新版本上线（`node tools/team/cloud-versions.cjs <环境ID> admin`：新版本 `normal`、流量 100%、备注是这个 SHA），先只查 admin：第三节第 1–4 条里和 admin 有关的（版本、迁移完成、cron 起来、告警地址、没有报错）。没问题再发 api：

```sh
backend/deploy/cloud_deploy.sh <环境ID> api <SHA>
```

api 也上线后，按第三节把两个服务一起再查一遍。

**脚本发布前自动核对（R4）**：先取最新的 main（GitHub 连不上就停）；只发已经合进 main 的提交；main 上的迁移文件一个都不能缺、内容也要一样。对不上会列出缺的、内容不一样的迁移文件，然后停下，不发布。
- 遇到这种情况多半是 SHA 写错了、发了落后的版本，换成 main 上最新的提交再发。
- 只有三种情况加 `--skip-main-check` 放行：回退到旧版本、GitHub 连不上又必须马上发、创始人同意发一个还没合并的版本。脚本会打印一行"没有核对"。
- 用放行参数发过**还没合并、又带迁移**的版本后，要先把它合进 main，再正常发布。不然下一次正常发布的 main 上没有那个迁移：发布前核对拦不住（它只和 main 比），admin 启动时会提醒"库比代码新"。

`cloud_deploy.sh` 用全量发布。云托管 CLI 也支持灰度（`--releaseType=GRAY`），但流量比例怎么设、能不能按比例放，我们还没试过；先在一次低风险发布上试，试通了再写进这一节。

## 三、发布后 10 分钟检查（团队做，只读；两个服务都发完以后做全套，只发了 admin 时先查 admin 那部分）

1. **版本**：`cloud-versions.cjs` 看两个服务的新版本都是 `normal`、流量 100%，备注是同一个 SHA；旧版本大约 14 分钟后自己缩到 0 个实例（10/16 实测）。
2. **启动**：`cloud-logs.cjs --out <自己临时目录里的文件> …` 取发布后 10 分钟的日志（日志原文只写进这个文件，终端只打印条数、页数、文件路径和一行查看提示），再用 `cloud_logs_show.py <文件> [关键词…]` 查（终端只显示时间、容器、接口字段和出错类别，日志正文不显示；关键词在正文里找，显示命中的行和条数；结果文件不要直接打开或贴出来），用关键词查到 `Application startup complete`；admin 还要看到"数据库已迁移到最新结构"、cron 起来（之后每分钟有"工具任务："一行）。**如果看到"数据库比代码新，没有迁移"**（群里同时有一条"启动时发现库里的迁移版本……比这版代码新"），而这次不是在回退，就是发错了版本（比如发了落后的分支），立即停下来查。
3. **告警地址**：启动日志里 `alert-probe` 那一行 `"configured": true`。搜 `not_configured` 应为 0 条。
4. **报错**：这 10 分钟里没有 5xx、没有 `Traceback`、没有"接口出错""接口成批失败"提醒。
5. **线上真用一次**：用开发者工具的测试号（不用创始人账号）打开首页、搜索、详情、查名单。
6. 结果写进 PR 或交接记录：时间、版本、SHA、每项结果。

任何一项不对，先停下来报给创始人，决定修还是回退。

## 四、小程序发版（创始人操作，团队准备）

1. 团队上传体验版（版本号、SHA 写进上传备注），出二维码和真机操作单。
2. 创始人用手机走一遍操作单（iPhone、安卓各一次）。
3. 提交审核：用团队准备的提审材料。
4. 审核通过后**选"分阶段发布"**（微信后台"版本管理"自带的灰度，[官方说明](https://developers.weixin.qq.com/miniprogram/dev/framework/quickstart/release.html)）：先放一部分用户，看一天——日报里没有新报错、微信后台"运维中心"没有新的 JS 错误、没有用户反馈——再全量。首发版本身可以全量。
5. 出问题：分阶段发布还没到全量的，先在后台停掉这次分阶段发布（还没收到新版的用户留在旧版）；已经全量的，用"版本管理"里的回退回到上一个线上版本（按钮名称以后台为准）。同时看后端要不要一起回退。

## 五、回退

### 什么时候回退

发布后出现下面任一情况、15 分钟内修不好，就回退：小程序打不开或大面积报错；数据写错（截止、名单、用户数据）；付款、注销等关键流程出错。

### 回退的顺序

**先回退 api，再回退 admin**：回退前按第一节第 2 条的命令看这次带了哪些迁移；都是加表、加列的，旧 api 在新的表结构上照常能跑；反过来，先动 admin 或库，新 api 可能用到还没回退的东西。删表、删列的迁移例外，见下面 admin 回退的第三条。

### api 回退

团队执行：

```sh
wxcloud version:list -e <环境ID> -s api --json      # 找上一个正常的版本名，如 api-055
wxcloud run:rollback -e <环境ID> -s api -v api-055 --noConfirm --detach
```

团队联系不上时，创始人也可以在云托管控制台 api 服务的版本列表里，把流量切回上一个正常的版本（以控制台界面为准）。回退后按第三节再查一遍。

### admin 回退

- **这次没有迁移**：和 api 一样回退。
- **这次有加表、加列的迁移**：回退到的那个旧版本**本身带着 R4 修复**（R4 那个 PR 部署之后发的版本）时，直接回退（用上面的 `wxcloud run:rollback`，不经过发布脚本；要是改用发布脚本重新发旧的 SHA，得加 `--skip-main-check`）：旧版 admin 启动时发现库里的迁移版本比代码新，会跳过迁移、照常启动，并在群里发一条"启动时发现库里的迁移版本……比这版代码新"。库里多出来的表和列留着，修好后发新版本时不用重新迁移。回退到 R4 之前的版本时，旧版 admin 遇到这种情况会起不来，要先在新 admin 容器里把库降到旧版本的迁移号再回退。
- **这次有删表、删列的迁移**：不能按上面"先回退 api"——旧 api 还在用被删掉的表和列，在新结构上会报错。顺序是：先在现在的（新）admin 容器里降库（`downgrade` 把表和列加回来，但里面的数据回不来），核对迁移号和表结构后，再回退 api、再回退 admin；要连数据一起找回，只能从备份恢复（见运营手册"数据库恢复"）。所以这类迁移合并前要创始人明确同意，部署顺序也是先 api 后 admin。
- 每个迁移的 `downgrade` 写了什么情况下不能自动降库（例如 0032：还有没到期的赠送天数、退款没办完时报错不执行）；真要降库时，团队写好命令和核对步骤，创始人在 admin 的"实例 → 终端"里前台执行并 `| tee` 保存输出。

### 回退之后

- 在交接记录里写：什么时候、为什么、回到哪个版本、数据有没有受影响。
- 修好后按第一节重新发。

## 六、演练

在一次低风险发布（比如只改文档的 api 版本）后，按第五节把 api 回退一次再恢复，记下实际耗时和步骤里不对的地方（R3）。要创始人同意部署。
