> **状态：创始人 10/4 确认按此方案做（D-047）。** 前提是省通管局确认免证；D-046 的其他收费门槛（付费证据、数据质量、稳定性、客服、付费协议）不变。

## 一、三条原则

1. **一切在微信里**（免证的前提）：机构版多账号在小程序里做；不给客户做网页后台、不对外开放数据接口；内部管理台只给自己用；给机构的周报以文件点对点发送。
2. **第一个收费功能“付款即执行”**：付一次钱跑一次名单比对，不存余额、不卖次数卡——没有余额到期、未用退款的问题。
3. **能自动的都自动**：任务失败自动原路退款；每日自动对账。开票起步人工、量大再自动化（agy 建议一开始就接电子发票服务，Claude 的取舍是量小时先人工）。

## 二、用户流程（名单比对按次包）

上传客户名单 → 免费预检（识别家数、可查范围）→ 显示价格、覆盖范围、退款规则 → 微信虚拟支付 → 收到支付成功推送后自动执行比对 → 出结果；失败自动原路退款。

免费额度不变（每天 1 次、每次 50 家以内）；付费档覆盖更多家数（如 100、200 家），价格按 [定价 v2](../商业/定价与套餐方案_v2_走量版.md) 访谈后定。

## 三、微信虚拟支付接入（官方原文核对）

出处：微信开放文档《小程序虚拟支付》（developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment.html）、`wx.requestVirtualPayment` 接口文档。

| 环节 | 做法 |
|---|---|
| 商品 | 模式选“道具直购”（`mode=short_series_goods`），不用代币；道具在小程序后台“虚拟支付”里上传、发布（也有 `/xpay/start_upload_goods` 等接口）；发布后约 10 分钟生效 |
| 下单 | 后端生成业务订单号（`outTradeNo`，不能重复），小程序调 `wx.requestVirtualPayment`，参数 `signData`（offerId、buyQuantity、env、currencyType、productId、goodsPrice（分）、outTradeNo、attach）、`paySig`、`signature` |
| 签名 | 支付签名 `paySig = hmac_sha256(appKey, uri + '&' + signData)`，AppKey 分现网和沙箱；用户态签名 `signature = hmac_sha256(sessionKey, signData)` |
| 发货 | 接“道具发货推送”`xpay_goods_deliver_notify`，同时用 `/xpay/query_order` 轮询兜底（两者至少一个，结合更可靠）；推送应答格式不对微信最多重推 15 次。以订单号唯一约束、事务内发货，防止重复执行 |
| 退款 | `/xpay/refund_order` 只是启动退款，之后查 `query_order` 到退款完成；另有退款推送 `xpay_refund_notify`。支付 180 天内退款平台退还手续费 |
| iOS | 苹果端订单由苹果结算（月末后 45–60 天、扣佣金）；苹果不支持开发者主动退款，用户在 App Store 申请时微信会推送 `xpay_subscribe_ios_refund_query_notify` 问询，需 3 秒内应答（连续 3 次超时则交苹果决定）。iOS 需微信 8.0.68 及以上 |
| 对账 | `/xpay/download_bill` 下载日账单，`/xpay/download_ios_settlement_bill` 下载苹果月账单，和本地订单自动比对 |
| 投诉 | `xpay_complaint_notify` 推送和投诉查询、回复接口，要接上 |

**先要核实的技术点：** 用户态签名要用到 `session_key`。后端跑在微信云托管、经 callContainer 只拿到 openid，现在没有 session_key；正常获取要用 AppSecret（按约定创始人不交给团队）。开发第一步核实云托管“开放接口服务”能否解决；不行就由创始人自己把需要的配置填进环境变量。`/xpay/*` 服务端接口同样要核实在云托管下的调用方式。

10/4 核实结果（微信云托管《开放接口服务》、虚拟支付文档、`code2Session` 文档，本机取回原文）：

- 云托管的“开放接口服务”可以免 access_token 调用微信后台接口（文档举例包括微信支付相关接口），不需要在容器里维护凭证；callContainer 请求头里自动带 openid、unionid 等用户信息。
- 但文档**没有写 session_key 怎么拿**；虚拟支付文档要求 session_key 用 `auth.code2Session`（`/sns/jscode2session`）获取。
- 两个办法：① 小程序 `wx.login` 拿 code，后台经开放接口服务调用 `/sns/jscode2session` 换 session_key（要在开放接口服务的接口权限里加上这个接口；能否不带 AppSecret 文档没写，**开通虚拟支付后在线上试**）；② 不行就由创始人自己把 AppSecret 填进云托管环境变量（团队不接触、不经手），后台用它换 session_key。
- 两种办法 session_key 都只在计算签名时用，不落库、不写日志。
- `/xpay/*` 服务端接口按开放接口服务的方式调用（同样要加到接口权限列表），线上验证。

## 四、数据和流程（Codex）

新增表：商品（SKU、价格（分）、行数上限）；订单（用户、业务单号、平台单号、商品快照、状态）；额度流水（任务、免费或付费来源、动作、唯一键）；退款（订单、金额、退款单号、状态）；对账（日期、订单、净额、差异）。以后做机构版再加机构和成员表。

流程：下单 → 支付推送或查单确认 → 事务内创建并执行任务 → 成功完成；失败原路退款 → 每日对账。

免费额度继续用现有 `AdvisorUsage`（用户×类型×北京时间日）；任务记录额度来源（免费或订单）。现有退额只减计数，要补“逐任务只退一次”的防重。

## 五、开发顺序（Codex 估计共 13–19 个工作日，不含审核等待）

1. 准备（2–3 天）：定商品、退款规则、页面；核实第三节的技术点；创始人在小程序后台开通虚拟支付、配置商品。
2. 支付闭环（5–7 天）：订单、签名、发货推送和查单、退款、对账。
3. 接入名单比对（3–4 天）：预检、付费档、订单页、退款入口。
4. 异常测试（3–5 天）：重复推送、并发、退款竞态、iOS、补单。

开发期间功能保持关闭；D-046 门槛达标后由创始人批准打开。

## 六、收费前要准备的文件（agy）

付费服务协议（服务边界、计费方式、免责）、退款规则（付款前显著展示；失败自动退）、明码标价（不虚构原价）、开票说明、隐私政策补订单和支付信息。都请律师确认。

## 七、一个人怎么撑住（agy）

退款、额度扣退、对账自动化；少量复杂客诉和对公合同人工。日常客服加开票加对账控制在每天 30–45 分钟；超过就暂停扩大，先改成自助。

## 八、不做的

- 不以免证替代 D-046 的其他门槛。
- 不凭小程序前端返回的“支付成功”执行任务，以服务端确认为准。
- 不首卖 AI、年卡、团队版、园区版。
- 不引导到站外付款；小程序里不写“联系我们签约购买”之类的话（是否允许待核实）。
- 不做余额过期清零。
