# AI 整理字段与报告：方案 v2（D-034）

> 2026-09-29。创始人要求"不是官网什么样就展示什么样，要用 AI 把官网的数据和内容整理好，还有报告"。Claude、Codex、agy、Grok 各自出方案后汇总，创始人同意"按 Claude 的建议做"。v1 经 Codex（技术）、agy（合规和审核）、Grok（用户角度）找漏洞后改成 v2，改动见第十节。开发、验收都以本文为准。

## 一、目标和范围

**目标：** 用户打开一份申报通知，不用读全文就知道"现在还能不能报、哪天截止、给什么支持、大致谁能报"；另有两份按数据汇总的报告。

**分两期（都在 R1 上线前）：**

| 期 | 编号 | 内容 | 说明 |
|---|---|---|---|
| 一期（10/6 前上线） | F3 | 申报状态 | 按核对过的截止日期自动算，不用人核（第四节） |
| 一期 | R-1 | 截止雷达 | 未来 7 / 14 / 30 天截止的项目清单和分组统计 |
| 二期（10/15 前上线） | F2 | 支持方式 | 分类标签：资金支持、贷款贴息、资格认定、入库备案、项目立项、其他；每个标签附原文句子 |
| 二期 | F1 | 申报对象（原文摘录） | 原文里写申报对象的那一句，注明"条件可能未列全，以原文为准" |
| 二期 | R-2 | 名单看板 | 先列最近的名单，再给统计数 |

**R1 不做：** 支持金额；申报条件逐条拆开；所需材料清单；AI 摘要、解读、问答；企业画像匹配。金额是红线字段、容易抽错；其余属于把 AI 写的文字给用户看，要先完成网信办登记，并按《人工智能生成合成内容标识办法》标明。

**对外不出现"AI"字样**（D-021）：小程序页面、提审材料都不写"AI 整理""智能"，写"整理""按原文摘录"。后台用了模型只是内部辅助，给用户看的都是核对过的内容或原文句子。

## 二、用户看到什么（小程序）

1. **详情页"要点"卡片**（只显示核对过的，没核的整行不显示、也不写"待核对"）：
   - 申报状态：见第四节；写明按哪种截止算，如"征集中 · 按企业申报截止 10 月 18 日"。
   - 支持方式（二期）：标签。
   - 申报对象（二期）：标题写"申报对象（原文摘录）"，内容是原文句子，下面一行小字"条件可能未列全，以原文为准"。
2. **搜索结果列表**：申报通知右侧显示状态角标（征集中、即将截止、已截止），只对有核对过截止日期的显示。筛选加"只看未截止"（征集中和即将截止都算）。
3. **报告页**（新页面，从首页入口和日历页进入），两个标签页：
   - **截止雷达**（一期）：顶部三个数（7 / 14 / 30 天内截止多少项）；下面的清单可按省份、部门、支持方式（二期起）筛选和分组，每条显示标题、截止类型和日期、剩余天数，点进详情；分页加载；可导出 Excel（沿用现有导出，小程序里用系统方式打开文件）。
   - **名单看板**（二期）：先是"最近 30 天公布的名单"清单（标题、发布日期、标题里的原文用词"公示 / 公布"、发文机关，点进详情和查名单）；再是统计：按年度、省份、名单类型的名单份数和名单条数。名单类型按标题归类（高新技术企业、专精特新、科技型中小企业、其他）。
   - 页面底部写明口径："只统计已收录网站的文件；截止雷达只含核对过的截止日期；名单条数是名单原文里的企业条数，公示期内的名单也计入，最终结果以原文为准。"
4. 所有页面仍保留"第三方整理 · 非政府平台"和原文链接。

## 三、数据怎么来（后台，二期）

1. **只处理申报通知**（名单、政策、其他类不抽字段）。
2. **规则先抽，按句子判断**：
   - 支持方式：每个标签有自己的关键词和优先级，按句子匹配，并排除否定和无关的说法（如"不予支持""不属于""不得重复申报"不算；"认定"只在"认定为/申报认定/认定工作"这类说法里算；"项目申报"只在同时出现立项、项目资金时算"项目立项"，否则不打标签）。**每个标签单独记一行，附自己的原文句子。**
   - 申报对象：找"申报对象""申报主体""申报单位""支持对象""申报条件"起头的句子，连同它后面的一句作为候选，最多 200 字；只摘录，不改写。
3. **模型再核**（配了密钥才调用，做法同截止日期）：发正文里相关的几段（按关键词取上下文，总长有上限），要求给出字段值和**原文照抄的句子**；句子在正文里逐字找不到的一律不用。记下规则和模型是否一致。只发政府公开的正文，不发用户数据。
4. **正文变了要重抽**：每份文件记正文的指纹（hash）。正文变了就重抽；已经核对过的字段标"原文已变化，请复核"，复核前不显示。
5. **流程**：每轮抓取里加一步（每天 2 轮，D-039） `youju extract-fields`，放在抽截止之后；同一份正文只抽一次（可重复运行，结果不变）。

## 四、申报状态怎么算（一期）

- 只用核对过的截止日期（`approved`），**已变更的截止（A7）不用**，改用新通知的。
- 一份通知有几个截止（如企业申报截止、推荐截止）：用第一个核对过的"企业申报截止"；没有就用最早的那个，并写明是哪种截止。几个都显示在详情里（现有的"另有截止"一行）。
- 按北京时间算。截止当天整天都算"征集中"；有具体时刻的，过了时刻算"已截止"。
- 截止前 7 天内（含当天）显示"即将截止"角标，同时也算"征集中"。
- 没有核对过截止日期的不给状态。

## 五、人工核对（创始人一人）

1. **一期不增加核对量**：状态和截止雷达只用已经核对过的截止日期。创始人照常在核对台核截止（先核 30 天内的）。
2. **二期新增"字段核对"页**：每张卡片一份文件，显示标题、截止日期、候选的支持方式标签和申报对象摘录、各自的原文句子（高亮）；按钮：通过 / 改了再通过 / 驳回；键盘快捷键。
3. **排队**：截止日期已核对、30 天内截止的在前；过期的不进队列。
4. **工作量**：本机库里 30 天内截止的文件 111 份。支持方式看标签和原句，约 10 秒；申报对象要读完原句，约 20 秒；每份约 30 秒，111 份约 1 小时。之后每天新增十几份，每天 5–10 分钟。
5. 核对留痕：谁、什么时候、从什么改成什么，写进访问日志（D-028）和字段表本身。

## 六、数据和接口

1. **新表**（迁移 0009，可回退）：
   - `document_fields`：每行一个字段值——文件、字段（support / audience）、值（支持方式的一个标签，或申报对象摘录）、原文句子、句子在正文里的位置、正文指纹、来源（规则 / 模型 / 一致）、状态（待核对 / 通过 / 驳回 / 原文已变化）、核对后的值、核对人、核对时间。同一文件同一字段同一值唯一。
2. **小程序接口**（只加字段，不改已有字段；旧版小程序不受影响）：
   - `GET /api/v1/documents/{id}`：加 `status`（`open` / `closing` / `closed`，含按哪种截止、日期）和 `fields`（只含通过的）。
   - 搜索接口：每条加 `status`；筛选加 `open=1`（征集中和即将截止）。
   - `GET /api/v1/reports/deadlines?days=7|14|30&province=&dept=&support=&page=`：截止雷达，分页。
   - `GET /api/v1/reports/lists?year=&province=&type=&page=`：名单看板，分页。
   - 都只用公开来源（一级）的文件，和现有接口一样；报告结果每个实例缓存 5 分钟。
3. **核对台接口**：列队列、通过、改、驳回，都要口令，都留痕。
4. **名单看板口径**：名单条数 = 名单文件里解析出的企业条数（已有的名单解析，查名单用的同一份数据，验收 A4 抽检过），同一份名单里同名去重；同一通知的几个网址只算一份。不展示任何个人信息（名单解析本来就不收个人列）。

## 七、合规和红线

- 截止日期、状态只用核对过的；支持方式、申报对象也只显示核对过的。
- 支持金额 R1 不抽、不显示。
- 名单状态照录标题用词（D-018）；名单看板只做计数和列清单，不判断"是否最终入选"。
- R1 不给用户看模型写的文字，对外不出现"AI"字样；核对台里的模型候选只给创始人看。
- 报告写明口径和收录范围，不写"全部""所有"。
- 隐私保护指引不用改（不新增个人信息）；提审材料的功能说明补"报告"页，类目仍是"工具 > 信息查询"（D-021）。

## 八、验收标准

| 编号 | 标准 | 怎么验证 |
|---|---|---|
| V1 | 详情页、列表只显示核对过的字段和由核对过的截止算出的状态 | 接口测试（未核的不返回）+ 真机各看 5 份 |
| V2 | 抽 30 条核对过的支持方式和申报对象，与原文 100% 一致 | 人工抽检，记在迭代文档 |
| V3 | 申报状态：当天、过时刻、跨天、多个截止、已变更截止都算对 | 固定日期的接口测试 |
| V4 | 截止雷达、名单看板的数字与数据库直接统计一致 | 接口测试 + 抽 3 个省手工核对 |
| V5 | 规则抽取在**另外标注的 50 份样本**（不用于调规则）上：支持方式精确率 ≥90%、召回 ≥80%；申报对象找到原句 ≥70% | 标注样本 + 脚本统计。**9/30 结果：未达标**——两批各 50 份（Grok 盲标、Claude 复核）：支持方式精确率约 75–80%、召回约 65%，申报对象约 20–30%；按退路申报对象先不上线（#85），支持方式只显示人工核对通过的 |
| V6 | 报告接口服务端 ≤500 毫秒（本机 1.7 万份文件测速库） | 测速脚本 |
| V7 | 核对 30 份文件（每份两项字段）用时 ≤15 分钟 | 创始人实测 |
| V8 | 正文变化后，已核对字段自动变为"请复核"且不再显示 | 接口测试 |
| V9 | 迁移可升级、可回退；重复运行抽取结果不变；未带口令的核对接口被拒 | 测试 |

## 十、风险

| 风险 | 应对 |
|---|---|
| 规则抽不准、模型没配 | 人核兜底；没核的不显示；V5 不达标就只上支持方式 |
| 创始人核不过来 | 一期不加核对量；二期只排 30 天内截止的；快捷键 |
| 官网改了通知 | 正文指纹变化即重抽，已核字段转"请复核"、复核前不显示 |
| 把"公示"当成可申报或已入选 | 只对申报通知算状态和抽字段；名单看板写明"公示期内也计入" |
| 多个截止日期赶错 | 状态写明按哪种截止；其余截止在详情里列出 |
| 报告被误读为"全部政策" | 页面写明口径和收录范围 |
| 挤占上线前的真机测试 | 两期都在 10/15 前完成，否则按第九节顺序砍 |

## 十一、v1 → v2 改了什么

- 分两期：一期（状态、截止雷达）不增加核对量，先上线；二期再上字段和名单看板（Grok 第 6 条、Codex 排期意见）。
- 申报对象改为"原文摘录"并注明可能不全（Grok 第 1 条）。
- 名单看板先列名单、再给统计，写明公示也计入；说明名单条数来自已有的名单解析（Grok 第 2 条、agy 第 3 条、Codex 数据意见）。
- "征集中"包含"即将截止"，筛选叫"只看未截止"（Grok 第 3 条）。
- 支持方式按句子判断、排除否定说法、每个标签单独留原句；验收看精确率和召回（Grok 第 4 条、Codex 抽取和模型意见）。
- 状态规则写清时区、当天、时刻、多截止、已变更截止（Grok 第 5 条、Codex 状态意见）。
- 接口只加不改、分页、缓存、迁移可回退；补 V8、V9（Codex 接口和测试意见）。
- 对外不出现"AI"字样（agy 第 1 条）；报告页口径（agy）。
- agy 提的"导出违规""10/6 提审"两条：导出已用系统方式打开文件；10/6 是后端发布，不是提审，提审仍是 10/26。
