# 开发流程

「有据」按标准的软件生命周期开发，针对"1 位创始人 + AI 团队"做了精简：每个阶段都有明确的产出和检查，但不写只为走形式的文档。

参考标准：ISO/IEC/IEEE 12207（软件生命周期过程）和 29148（需求工程）的阶段划分；日常协作采用 GitHub Flow（功能分支 + 拉取请求 + 自动检查）。

## 一、生命周期与我们的做法

| 阶段 | 标准要求 | 我们怎么做 | 产出放在哪 |
|---|---|---|---|
| 需求 | 需求明确、可验证 | 总方案定义做什么和为什么；执行手册定义每一步的完成标志；每个迭代的任务写成 GitHub Issue，并写明完成标志 | `docs/有据_产品定位与商业开发总方案_v7.md`、`docs/有据_执行手册_v1.md`、GitHub Issues |
| 产品设计 | 界面和交互在开发前确认 | 用户看得到的功能，先出信息架构和可点击原型；Grok 做竞品界面对比，agy 做合规审阅；**创始人确认后才开发界面**，确认和修改意见记进迭代记录 | 原型链接、`docs/迭代/` |
| 技术设计 | 关键决定有记录、可追溯 | 架构和技术上的关键决定写成架构决策记录（ADR）：背景、选择、放弃了什么、后果 | `docs/adr/` |
| 开发 | 版本控制、代码规范 | 每项任务一个分支（`feat/`、`fix/`、`docs/`、`chore/`）；提交信息用约定式格式（如 `feat: …`）；代码风格由 ruff 自动检查 | Git 历史 |
| 测试 | 分层测试、可重复 | 单元测试（解析、日期、网址等纯逻辑）；集成测试（真实 PostgreSQL）；真实网页样例测试（保存的政府网站列表页）。小程序上线前加真机端到端测试 | `backend/tests/` |
| 审阅 | 独立审查 | 每个拉取请求（PR）至少经过一名 AI 成员审阅：agy 看架构、安全、合规；Grok 看边界情况和失败场景。Claude 逐条处理并在 PR 里回复 | GitHub PR |
| 集成 | 自动构建和检查 | GitHub Actions 在每个 PR 上运行代码检查和全部测试；不通过不合并 | `.github/workflows/ci.yml` |
| 发布 | 版本管理、发布审批 | 开发期版本号 `v0.x`；每次发布写更新说明；**小程序提审、服务器上线必须由创始人批准** | GitHub Releases、`docs/迭代/` |
| 运维 | 监控、备份、事故处理 | 来源健康监控和告警；数据库每日备份；出现事故写复盘 | `docs/迭代/`、运维手册（R1 前补齐） |

## 二、一项任务从开始到完成

1. **开 Issue：** 写清楚要做什么、完成标志是什么，归入当前迭代的里程碑。界面相关的任务附上已确认的原型页面；原型没确认，不写界面代码。
2. **建分支：** 从最新的 `main` 拉出分支。
3. **写代码和测试：** 同一工作区同一时间只有一名 AI 成员写代码（见 AGENTS.md）。
4. **本地检查：** `uv run ruff check .` 和 `uv run pytest` 都通过。改了小程序或接口的，还要在开发者工具里连本机后台实际操作（AGENTS.md 第 8、9 条）。本机后台的库用 `tools/team/fresh-test-db.sh <库名>` 新建（前提：本机运行过 `wxcloud login`、本机 MySQL 在跑）：数据是线上最新的公开内容（每天 4:50 导出，不含用户数据、密钥、日志和下架的文件）；把它最后打印的连接地址设成本机后台的 `YOUJU_DATABASE_URL` 再启动，测试窗口名带上它打印的"数据MM/DD"。
5. **提 PR：** 按模板写明改了什么、怎么验证的、有什么风险，并关联 Issue。
6. **审阅：** agy 和/或 Grok 只读审阅；Claude 处理意见，处理不了的写明原因。
7. **CI 通过后合并：** 使用 squash 合并，`main` 始终保持可运行。
8. **关闭 Issue：** 在迭代记录里更新进展。

## 三、完成标准（每个 PR 都要满足）

- 功能满足 Issue 里写的完成标志；
- 涉及界面的改动：界面与已确认的原型一致，有出入的地方经创始人同意；
- 新逻辑有测试，本地和 CI 都通过；
- 没有把密钥、`.env`、用户数据提交进仓库；
- 涉及数据抓取的改动遵守合规红线（robots、限速、不绕过防护）；
- 需要说明的地方更新了文档（README、ADR 或迭代记录）；
- 至少一名 AI 成员审阅过，意见已处理。

## 四、迭代节奏

- **两周一个迭代。** 周一定计划，每天 Claude 写日报，周五演示。
- **迭代结束：** 演示做出来的东西，回顾哪里顺、哪里不顺，记录在 `docs/迭代/Sprint-NN.md`。
- **创始人参与：** 看周五演示（30 分钟），批准发布，在需要时做产品决定。代码合并由 Claude 按上面的完成标准执行，不需要创始人逐个点合并。

## 五、和大公司流程相比，我们省了什么、补在哪里

| 大公司常见做法 | 我们的做法 | 补救措施 |
|---|---|---|
| 独立测试团队 | 自动化测试 + AI 审阅 | R1 上线前做一轮完整的端到端和真机测试 |
| 独立安全团队 | agy 安全审阅 + 依赖检查 | R3 收费前请外部机构做一次安全评估 |
| 专职运维 | 监控告警 + 备份脚本 | R1 前写运维手册：备份恢复演练、故障处理步骤 |
| 分支保护强制审阅 | 私有仓库免费版不支持强制分支保护，按流程约定执行 | 所有改动都走 PR 和 CI，合并记录可查 |
