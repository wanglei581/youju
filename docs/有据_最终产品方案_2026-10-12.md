## 一句话结论

先把有据做成**申报顾问每天早上看一眼的"截止和名单"工具**：不用登录，就能查通知、看哪些项目快截止、查客户上了哪些名单、看本机 20 家客户各涉及哪些通知。每条都能点回政府原文。
AI、奖励和引荐、认定条件对照从小程序里拿掉，付费放到最后一步。目标是 **11 月中旬前上线**（最快 10 月底），卡点是备案。

## 一、为什么现在"走不完全程"

1. **核心卖点靠人工核对，而只有你一个人能核。** 管理台有 8 个要人工处理的队列，两周下来一条都没核。所以申报日历、截止雷达是空的，所有截止都写"未核对"，申请条件、转发合并也都是 0。
2. **上线要过的几道门，一道都还没开始办。** 备案、律师、虚拟支付、AI 登记都没动，做好的功能都卡在门后。内测版看上去到处是半成品，原因就在这里。
3. **功能铺得太开。** 提审版 18 页，内测版又多 11 页，而且互相重叠：日历和雷达、查名单和看板、按客户筛通知和客户相关通知表。AI、付费、奖励、引荐都是在没有用户证据、没过门槛之前就做了。
4. **第一印象坏在服务器上。** 接口服务空闲以后，第一次打开要失败 1–2 分钟，页面提示"网络不太好"。10/11、10/12 各实测到一次。
5. **数据有杂项。** 近 30 天 207 份"申报通知"里，约 18% 不是企业能报的事（职称评审、征求意见、验收和绩效、比赛、遴选服务机构等）。
6. **还没有一个真实用户**，所以没有反馈。

已经做扎实的部分：70 个政府栏目每天抓两轮从没断过，现有 1797 份文件、461 份名单，每条都能回原文，附件存了副本，可以导出。9 月定的 5 个差异点里，"每条能回原文"这一条已经做到；"截止可信""多客户跟进"这次补上；"到地市"放第 2 步；"价格透明"放第 4 步。

## 二、首发版本长什么样

不登录、不收费、没有 AI。底部还是三栏：**首页、文件、我的**。

**主流程一：盯截止（顾问每天早上）**
首页看"7 天内截止"（只放人工核对过的）→ 点"截止"看未来 30 天 → 点进详情，看截止类型、日期、原文那句话和附件 → 复制原文链接，或者导出发给客户。

**主流程二：查客户（顾问随时）**
首页点"我的客户"，本机最多存 20 家（名称、省份、产业方向）→ 按通知列出：一条通知一行，写明涉及哪几家客户、什么时候截止 → 导出一张表。
首页点"查名单"，输入企业名 → 看在哪些公示/公布名单上；查不到时写"在已收录的 N 份名单中没查到"，并能看到收录了哪些名单。

| 页面 | 首发版里的样子 |
|---|---|
| 首页 | 搜索框（申报/名单/政策三种范围）；三个入口：查名单、截止、我的客户；"7 天内截止"（只放核对过的，最多 5 条，没有就不显示这一块）；"本周新增申报通知"（已剔除杂项） |
| 截止 | 原申报日历 + 截止雷达合并成一页：未来 7/14/30 天，可切月历；按省份、部门筛；"只看已核对"开关；显示规则见第四节 |
| 查名单 | 原查名单 + 名单看板合并；写清"拿哪些名单比的" |
| 我的客户 | 原"按客户筛通知"升级：本机存，不上传；按通知去重；可导出 |
| 搜索 | 外面只放地区、类型、时间、部门、只看未截止，其余收进"更多" |
| 详情 | 一份通知有几条截止（企业申报、推荐、材料报送），逐条写类型，不挑一条代表整份 |
| 文件、我的、关于 | 关于页填上真实的备案号、联系邮箱、纠错和侵权投诉渠道（首发没有纠错页，靠邮箱） |

## 三、每个功能怎么处理

| 功能 | 处理 | 理由 |
|---|---|---|
| 首页、搜索、详情、文件、我的、关于 | 保留，按上表改 | 主流程要用 |
| 申报日历、截止雷达 | **合并**成"截止" | 同一批日期，没必要两个入口 |
| 查名单、名单看板 | **合并** | 同一件事 |
| 按客户筛通知 | **升级**成"我的客户" | 顾问一人盯多家，不用登录 |
| 认定条件对照 | **删掉** | 不在主流程里，容易被看成"判断能不能报" |
| 关注、新建关注、纠错、我的数据、同意协议 | 第 3 步 | 要律师定稿；仍用代码包里的开关关着（D-056），律师定稿后作为新版本提审 |
| 批量工具 4 页（批量名单比对、客户相关通知表） | 第 3 步 | 要登录和协议；首发先用本机"我的客户"顶上 |
| 客户工作台 30 天、订单 | 第 4 步 | 付费门槛一个都没过 |
| 奖励规则、请同行来用、补截止日期 | **删掉** | 增加条款和人工负担，还有诱导分享的风险；核对不能靠用户任务 |

| 管理台：截止核对 | 保留，每天第一件事 | 首页和截止页的来源 |
| 管理台：类型纠正 | 改成规则自动剔除杂项 | 提审前先把存量跑一遍 |
| 管理台：侵权投诉 | 保留 | 法定渠道 |
| 管理台：申请条件、支持方式和申报对象、转发合并、纠错处理、来源接入 | 暂缓 | 一个人顾不过来；转发合并放第 2 步，纠错放第 3 步，地市来源放第 2 步以后 |

"删掉"的代码都留在 git 历史里，以后需要能找回来，做过的工作不会丢。奖励和 AI 的后端开关一律关掉、不再维护，两个月内没有恢复计划就清理。

## 四、截止日期怎么办（要你拍板）

**抽查结果**：从本机副本里随机抽 40 条机器抽出的截止候选，逐条对照原文那句话。40 条的日期都能在那句话里找到，而且确实是那句话说的截止时间；3 条的"截止类型"可以商量（推荐截止还是材料报送截止）；5 条本身不是企业能报的事，应该被类型规则剔掉。另外，线上抽的 60 份近期申报通知里有 13 份没抽到候选（原文没写日期，或者写在附件里）。

**新规则**（四位专家挑错后收紧的版本）：
- **7 天内到期的、首页上的：只显示人工核对过的。** 没核对的照样列出标题，但不写日期，写"截止未核对，以原文为准"。
- **8–30 天到期的：可以显示机器从原文摘出的日期。** 同一行必须原样附上原文那句话，并标"机器摘录·未经人工核对"；截止页顶部常驻一句"机器摘录仅供参考，以原文为准"。摘不到的写"截止未核对"。
- 只显示能在**当前正文**里找到那句话的候选。原文改了，旧候选立刻撤下，等重新摘。已经过期的候选不算"未截止"。
- 导出的表也这样写：截止列标"（机器摘录）"，旁边一列放原文那句话；表头写"截止日期以原文为准"。
- 你的工作量：提审前一次核完 7 天内到期的（预计几十条，约 15–30 分钟）；上线后每天早上 5–10 分钟，核新进入 7 天窗口的。哪天没核，产品也不会空，只是那几条不写日期。

这是对 D-051（"没核对的不显示日期"）的部分修改，所以需要你确认。如果不同意，就退回原规则：你每天固定核 20 分钟左右，断几天，截止页就会变空。

- 标题后面粘着正文的问题已修好（10/12）。

## 六、和一体机的关系

**不做功能联动。** 四位专家意见一致。一体机的用户是求职者，数据是岗位和招聘会，场景是线下大屏打印；有据的用户是申报顾问和企业，数据是科技、工信部门的申报通知和名单。硬凑只会让两边都更分散，也会让小程序类目和审核变复杂。两边能共用的，只有公司主体、开发方法和运维经验。

## 七、上线后 30 天看 3 个数

1. **截止覆盖**：7 天内到期的申报通知，100% 人工核对；30 天内到期的，有日期可看（核对过的或机器摘录）≥ 80%。
2. **真实使用**：至少 30 人走完"首页 → 原文或导出"，其中至少 10 位是顾问；第二周还在用的顾问至少 5 位。低于这个数就先停新功能，去访谈。
3. **稳定**：接口请求 99% 在 3 秒内成功（看访问日志）。

## 八、最大的风险

1. **备案拖得久**：现在就办，开发同时进行。
2. **核对断档**：7 天窗口没核的照样列出标题，只是不写日期；连续 3 个工作日没核，首页写"今日未更新"，不拿旧数据充新鲜。
3. **机器摘错日期**：只显示能在当前正文里找到原句的；原文一改就撤下；每处都附原句、写明以原文为准。
4. **再次分散**：见第五节最后一句。

## 九、仓库和文件大小

- **代码仓库不大**：607 个文件，GitHub 上 11 MB，不用动历史。最大的文件是几张设计效果图（每张 200–540 KB）。
- **本机一共约 3.4 GB，大头不是项目本身**：本机数据库的操作日志 1.6 GB（测试反复建库删库留下的，清掉不丢数据）；旧的 PostgreSQL 数据 417 MB（9/28 换 MySQL 时特意留的）；一份过时的本地数据副本 139 MB；Python、Node 运行环境约 0.4 GB；10 个工作目录。按下面的建议清理，能省约 2.2 GB。
- **清理建议**：清数据库日志，并关掉本机开发库的日志；删旧 PostgreSQL 数据和过时副本（这两项是删数据，需要你同意）；用完的工作目录随手清。
- **文档**：把已经被取代的早期方案（v1–v5.1 等十几份）移进 docs/归档/，docs 目录下只留现行文件。
- **删功能以后代码还会再少一些**（Codex 估：小程序源码少 120–180 KB，后端少 200–350 KB）。体积本来就不大，主要是少了维护负担。
