## 0. 一页结论

**品牌：「有据」。** 小程序全称"有据申报与行业助手"，AI 助手叫"小据"。
**口号：** 每条都有出处的 AI 行业情报助手。

**定位：** 面向需要定期跟踪政策、申报和行业动态的职场人与服务机构。覆盖全国全行业的政策、申报通知、认定名单、行业数据和报告线索，每条都能点回官方原文；有变化自动提醒；一键整理成 Excel、Word、PPT。

**已拍板的决定**

| 事项 | 决定 |
|---|---|
| 范围 | **全国版**：首发覆盖国家部委和 31 个省级科技、工信部门，之后扩展到其他省级部门和 36 个重点城市 |
| 公司 | 有限责任公司；注册资本先设 10–20 万元，申请 ICP 经营许可证前增资到 100 万元 |
| 团队 | 1 位创始人 + Claude + agy + Grok；后期可能加入 Codex（GPT-6） |
| 名称 | 「有据」（三方投票一致）；备选「见源」「引据」 |
| 收费模式 | **套餐卡式订阅**（季卡/年卡预付、不自动续费）+ **AI 点数加油包** + **按份购买**；首页主推个人年卡 ¥298；机构年卡走对公合同 |
| AI | 后台用 AI 生产和质检数据；前台 AI 功能在网信办登记完成后开放 |

**五个核心判断**

1. **能做，而且应该先做出来。** 数据主要来自政府公开文件；首次全国抓取（2026-09-26）中，93 个首发栏目里启用的 72 个全部成功，覆盖 28 个省和国家部委，一轮约 40 秒。真正的门槛是持续、准确地维护数据，这件事主要交给 AI 完成，你每周抽检约 1–3 小时。
2. **不和免费 AI 比"帮你搜、帮你写"。** 我们卖的是它们做不好的：跨地区、结构化、每条可核验、会主动提醒、能直接交差的结果。
3. **个人带来流量，机构带来收入。** 全国版让个人流量池变大；收入主力仍是申报顾问和咨询团队。
4. **AI 是"员工"，不只是聊天框。** 后台有 AI 资料员（抽取）和 AI 质检员（交叉校验），前台有小据（问答、速读、资格自测、周报、PPT）。一人团队能维护全国数据，靠的就是这些 AI 员工。
5. **合规决定上线顺序。** 生成式 AI 功能要等网信办登记；小程序内收费要先有 ICP 经营许可证，而许可证要求主要人员社保（实务中通常 3 人）。所以分三次上线，每一步都合规。

**分三次上线**

| 版本 | 内容 | 前提 | 预计时间 |
|---|---|---|---|
| **R1 免费版** | 全国搜索、详情卡、申报日历、名单库、订阅提醒、Excel/Word 导出。不含生成式 AI 界面 | 公司、小程序认证与备案 | 2026 年 12 月中旬 |
| **R2 AI 版** | 小据问答、AI 速读卡、资格自测、AI 周报底稿 | 网信办登记、"深度合成-AI问答"类目 | 2027 年 1 月（取决于登记进度） |
| **R3 付费版** | 会员、AI 点数、机构年卡、客户名单比对、PPT 导出 | ICP 经营许可证（需增资和 3 人社保） | 标准路径约 2027 年 5 月中旬–6 月初；加速路径约 3 月 |

**首个验证目标：** R1 上线后 6 周内（2027 年 1 月底），周活机构 ≥20 家、书面采购意向 ≥10 家。达到了才招人、申请许可证。

**12 个月投入：** 约 ¥14–25 万（主要是收费阶段新招的 2 人），不含你本人生活费。如果一直不进入收费阶段，约 ¥3–6 万。

### 2.3 从"数看三医"学什么

你朋友的小程序验证了"垂直资料库 + 分类筛选 + 悬浮 AI 入口 + 会员额度"的模式。可以借鉴：首页分类图标、多维筛选、按"次数"设计权益。我们横跨行业和地区，重点是申报、名单、订阅和导出。医疗行业可以考虑和它合作导流，而不是竞争。

### 2.4 护城河

护城河来自三样东西的积累，而不是 AI 模型本身：
1. **全国结构化数据资产。** 持续抓取、AI 抽取并经质检的政策库、申报节点库和名单库，时间越长越难追赶。
2. **工作流粘性。** 用户保存的订阅、客户名单、报告模板和历史周报。
3. **微信搜一搜里的落地页。** 全国版能产生数万个"XX 年 XX 省高企名单""XX 申报截止时间"的页面。

## 3. 产品定位

### 3.1 名称：「有据」

**怎么定的：** Claude、agy、Grok 各自提出候选，共 20 多个。经过联网冲突初筛（淘汰了"知脉"：已有同名 App；"申迹""知申"：已有在营公司），再按五个维度（契合定位、好读好记、冲突风险、可延展、合规安全）打分，三方第一票都投给了「有据」。

| 名称 | 结论 |
|---|---|
| **有据**（选定） | 直接表达"有理有据、每条有出处"，正对 AI 容易编造的痛点；两个常用字，好读好记；不含敏感词，不像政府平台 |
| 见源（备选 1，agy 提出） | "洞见行业、溯见信源"；可能更容易注册商标；AI 助手可叫"小源" |
| 引据（备选 2，Grok 提出） | "引用为据"；更贴近"点回原文" |
| 申历、行脉、溯业、研策星 | 未选：分别存在"申"易被理解为上海简称、"行"是多音字且"行脉"易被理解为诊脉、"溯"字生僻、偏咨询公司感等问题 |

**需要你确认：**
- **商标：** 「有据」是常用词，商标可能难以独占。先在[中国商标网](https://sbj.cnipa.gov.cn/)查第 9、35、42 类近似商标；被占用就换「见源」。
- **小程序重名：** 注册小程序时系统会检查。
- **域名：** `youjuzs.com`、`youjuzs.cn`（"有据助手"）在 2026-09-26 查询时未被注册；`youju.com`、`youju.cn` 已被占用。

**使用规则：** 对外统一描述为"企业服务类信息查询与整理工具"。小程序名称、简介和宣传中不用"政策、时政、官方、国家、政务、新闻"等字样作为名称；正文可以正常提到"政策文件"。

### 3.2 用户分层：谁用、谁付钱

| 层级 | 用户 | 高频任务 | 在产品里的角色 |
|---|---|---|---|
| **付费核心** | ① 申报顾问/科技服务机构（1–20 人） | 每周确认各地申报窗口、名单公示与正式状态、客户是否上榜 | 机构年卡主力；口碑传播者 |
| | ② 咨询公司/智库分析师 | 按客户指定的"地区×产业×时间"交付带出处的底稿 | 机构年卡、按份购买 |
| | ③ 企业政府事务/战略/政策研究岗 | 跟踪本行业政策，给领导写周报 | 个人年卡（首页主推），进而推动公司买机构年卡 |
| **次付费** | ④ 园区企服/招商、商协会 | 给入驻企业或会员推送申报提醒；按称号筛选目标企业 | 白标服务、名单包 |
| **流量** | ⑤ 普通职场人、学生、中小企业主 | 查一份政策、找一份报告、查自家企业是否入选 | 免费用户；搜一搜流量；分享传播 |

### 3.3 价值主张：三个承诺

1. **全：** 一个入口查全国和各地的政策、申报、名单、数据和报告线索。
2. **准：** 每条结论标明发文机关、文号、日期、原文链接和附件行；公示就写公示，查不到就说"无法确认"。
3. **省事：** 有变化才提醒；勾选即可导出，直接交给领导或客户。

### 3.4 产品原则

- **结果优先：** 先给结论和关键字段，再展开原文。
- **每条可回源：** 没有原文依据的数字、日期、名单状态，不作为确定事实展示。
- **覆盖如实标注：** 每个"行业×地区"标明"深度覆盖 / 仅政策 / 暂未覆盖"。
- **AI 只基于已入库、有权使用的资料回答：** 证据不足就说不足；数字和日期从结构化字段读取，不让模型"写"。
- **不搬运版权内容：** 商业报告只做题录、≤200 字摘要和原站链接。

### 3.5 明确不做

不代写申报材料或"包装"企业数据；不提供研报全文下载；不抓取设有反爬措施的系统（如国家企业信用信息公示系统）；不做时政新闻和评论；不提供投资建议。

## 4. 产品功能

### 4.1 信息架构

```text
底部导航：  找答案   │   关注   │   文件   │   我的
             │           │          │          └ 会员/点数/机构兑换/客户名单/设置/纠错
             │           │          └ 导出记录、周报历史、重新下载、发到电脑
             │           └ 我的订阅（行业×地区×类型）、本周变化、申报日历、客户动态
             └ 搜索框 + "问小据"（R2 起）+ 快捷入口：
               [查申报] [查名单] [查政策] [找报告] [看数据] [行业导航]
```

### 4.2 按版本的功能清单

**R1 免费版（2026 年 12 月中旬）——不含生成式 AI 界面**

> 2026-09-27 调整：按[决策记录 D-017](./决策记录.md)，R1 争取 10 月 31 日前上线，范围有删减，部署改用微信云托管，见 [Sprint 3](./迭代/Sprint-03.md)。

| 功能 | 说明 |
|---|---|
| 全国搜索与筛选 | 关键词、文号精确搜索；按行业（国标门类/大类）、地区（省/市）、类型、发文机关、时间、状态筛选 |
| 详情卡 | 结构化字段（发文机关、文号、发布/截止日期、支持金额、申报条件、适用行业/地区、名单状态）+ 原文链接和附件；不展示 AI 写的摘要 |

| 行业导航 | 全行业分类树，每个行业显示覆盖程度 |
| 关注订阅 | 按"行业×地区×类型"订阅；站内提醒 + 服务号通知 |
| 导出 | 所选结果导出 Excel、Word；电脑版微信直接另存为，手机端预览或由用户选择会话转发 |
| 增长 | 入选海报、申报倒计时卡、覆盖申请、纠错、搜一搜收录 |

**R2 AI 版（网信办登记完成后，预计 2027 年 1 月）**

小据问答、AI 速读卡、单家企业资格自测、AI 周报底稿（Word）。所有 AI 输出都带"AI 生成"标识和出处。

**R3 付费版（取得 ICP 经营许可证后）**

季卡、年卡会员；AI 点数和加油包；按份购买；机构年卡兑换码；客户名单比对 v1；邮件周报；PPT 导出。

**R5（付费上线后 3–12 个月）**

**模型与平台：**
- **前台交互**（问答、速读）：通过微信云开发 AI 能力调用已备案模型（如 DeepSeek、混元），它可以生成"深度合成"类目需要的算法备案材料（[官方文档](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloud/guide/extensions/extend/ai/model.html)）。

- 按任务难度路由：日常抽取和问答用低价快速模型，长报告用能力更强的模型。

**评测体系（上线门槛）：**
- **金标集：** 100 个真实问题（含 20 个以上应拒答的问题）+ 200 份抽取样本，由 Grok 设计题目、创始人确认答案。
- **每次改提示词或换模型都自动回归评测。** 门槛：
  - 人工确认后的关键字段 100% 正确；人工确认前抽取准确率 ≥95%；
  - 有依据的问题回答正确率 ≥90%；应拒答问题的拒答率 ≥90%；
  - 引用 100% 能在原文中找到。

**成本控制：** 按文档缓存速读卡和抽取结果（同一文件只算一次）；高频问题语义缓存；批处理放在离峰时段；免费用户每日限次；Agent 限制最大步数。

- **关口 G1（R1 发布前）：** 数据质量达标（§4.4 评测门槛；栏目周成功率 ≥95%）。
- **关口 G2（R1 后约 6 周，2027 年 1 月底）：** 周活机构 ≥20 家、书面采购意向 ≥10 家 → 招人、增资、申请许可证。
- **关口 G3（R3 后 8 周）：** ≥10 家机构付费；个人付费转化率有稳定数据 → 扩城市、考虑再招人。
- **观察指标：** 免费用户周活、搜一搜访问、订阅数、导出数、续购率。

## 6. 技术方案

### 6.1 总体架构

```text
                ┌──────────────── 微信生态 ────────────────┐
  用户 ────────►  小程序（原生）   服务号（提醒）   搜一搜（收录）
                └──────────────────┬───────────────────────┘
                                   │ 云托管调用 / HTTPS
                 ┌─────────────────▼──────────────────┐
                 │ API 服务（FastAPI）                  │── 虚拟支付 / 兑换码（R3）
                 │ 搜索 · 详情 · 订阅 · 导出 · 小据（R2） │── 邮件 / 企微机器人
                 └──────┬────────────────────┬────────┘
                        │                    │
         ┌──────────────▼───────┐   ┌────────▼────────────────────┐
         │ PostgreSQL            │   │ 任务队列（Redis）              │
         │ 业务表 + 中文全文检索    │   │ 采集 · 解析 · 抽取 · 校验 · 导出 │
         │ + pgvector 向量检索    │   └────────┬────────────────────┘
         └──────────────────────┘            │
                   ▲               ┌─────────▼────────────────────────────┐
                   │               │ 采集与 AI 员工（Python worker）          │
         ┌─────────┴──────────┐    │ 抓取（httpx / Playwright）→ 脱敏 → AI 抽取 │
         │ 运营后台（Web）      │    │ → 双模型校验 → 企业消歧 → 去重关联          │
         │ 来源/审核/更正/订单  │    └─────────┬────────────────────────────┘
         └────────────────────┘              │
                               对象存储（附件、导出文件）· 已备案大模型 API
```

### 6.2 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 小程序 | 微信原生（沿用 `apps/miniapp`） | 已有四栏骨架；只做微信生态时最稳 |
| 后端 | Python 3.12 + FastAPI | 采集、解析、AI、文档生成都是 Python 生态最强 |
| 数据库 | PostgreSQL 16 + 中文分词（zhparser 或 pg_jieba）+ pgvector | 一个库解决业务数据、全文检索和向量检索 |
| 检索 | 三路混合：文号和机关精确匹配；行业、地区代码、日期结构化过滤；关键词（BM25）+ 向量语义检索；重排序 | 用户最常搜的文号必须一搜就准 |
| 任务队列 | Redis + ARQ（或 Celery） | 抓取、解析、导出都是异步任务 |
| 采集 | httpx（静态页和列表接口）+ Playwright（只用于没有防护、用脚本加载列表的页面；防护页和拒绝爬虫的网站不渲染、不绕过）+ trafilatura（正文）；每个栏目用配置化规则，由来源接入 Agent 辅助生成 | 已验证：多数政府栏目是静态页，少数需要浏览器渲染 |
| 附件解析 | pdfplumber（表格型 PDF）+ RapidOCR（扫描件） | 名单多为 PDF 表格 |
| AI | 前台：微信云开发 AI；后台：阿里云百炼/腾讯云；结构化输出（JSON Schema）；双模型交叉校验；语义缓存 | 合规材料现成；按量计费 |
| 导出 | openpyxl、docxtpl、python-pptx、WeasyPrint 或 LibreOffice | 同一份数据渲染多种格式；文件写入 AI 标识元数据 |
| 运营后台 | R1 在现有轻量管理台上扩展；之后视工作量换 Vue 3 独立后台 | 先够用 |
| 部署 | R1：腾讯云轻量服务器（4 核 8G）+ Docker Compose + 对象存储；R3 后：微信云托管 + 云数据库 PostgreSQL | 前期成本最低，后期降低运维负担 |

### 6.3 数据管线

```text
来源登记 → 定时检查栏目（每天 1–4 次）→ 发现新条目/附件 → 抓取正文（记录指纹和版本）
  → 隐私脱敏 → AI 抽取 → 双模型交叉校验 + 规则回查原文
  → 企业消歧（全称精确 → 别名 → 存疑转人工）→ 去重与关联
  → 分流：非关键字段高置信自动发布；关键字段或低置信进审核台
  → 发布（不可变版本）→ 更新索引 → 匹配订阅 → 提醒/周报
检查失败 → 连续 3 次告警并生成工单；前台显示"截至上次成功检查"，绝不显示"无更新"
```

### 6.4 核心数据表

- **来源与资料：** `sources`、`documents`、`document_versions`、`attachments`
- **结构化事实：** `facts_application`（申报事项）、`list_entries`（名单行，含原文企业名、匹配方式和置信度）、`companies`（企业底表）、`tags`（行业/地区/类型）、`evidence_spans`（字段对应的原文位置）
- **AI：** `ai_runs`（模型、提示词版本、输入输出摘要、成本）、`eval_cases`、`eval_results`
- **用户与交付：** `subscriptions`、`digests`、`exports`
- **商业：** `users`、`orgs`、`seats`、`orders`、`points_ledger`、`redeem_codes`
- **审计：** `audit_logs`

### 6.5 现有代码怎么处理

| 现有部分 | 处理 |
|---|---|
| `apps/miniapp`（原生小程序，四栏） | 保留并扩展；拿到 AppID 后编译验证。`sitemap.json` 目前禁止索引，R1 上线时开放详情页 |
| `services/api`（标准库 HTTP + SQLite，5 项测试通过） | 作为规格参考，重写为 FastAPI + PostgreSQL；保留其权限分级、待审隔离、版本和导出规则 |
| `services/api/static/admin.*` | 在 R1 扩展为审核台 |
| `designs/产品原型` | 补"申报日历、名单库、入选海报、订阅卡、问小据"页面后再评审 |

### 6.6 合规的技术落实

- 所有 AI 功能都有开关；登记完成前前台开关保持关闭。
- AI 输出显示"AI 生成"标识；页面公示所用模型名称和备案/登记号。
- 导出文件在封面或页脚注明 AI 生成部分，并在元数据中写入标识（GB 45438-2025、《人工智能生成合成内容标识办法》）。
- 用户输入和 AI 输出经过微信内容安全接口。
- 自然人信息入库前脱敏；网络日志留存不少于 6 个月；数据库每日备份并定期演练恢复。

## 9. 风险与应对

| 风险 | 早期信号 | 应对 |
|---|---|---|
| 全国范围数据质量失控 | 人工确认前准确率连续两周低于 90%；你的抽检时间超过每周 3 小时 | 触发止损规则：停止新增栏目，先改抽取质量；覆盖程度如实标注 |
| 网信办登记耗时长 | 提交后 8 周仍无结果 | R1 不依赖登记；AI 功能保持关闭，持续跟进 |
| ICP 许可的人员门槛 | 试用信号不足以支撑招 2 人 | 先把免费版做到有稳定机构使用；需要时可在确认合法后用咨询服务合同先收入 |
| 用户觉得"政府网站 + 免费 AI 就够了" | 试用机构两周后不再打开 | 只卖做不好的：跨地区汇总、截止日历、名单状态、客户比对、可交差的表 |
| 推送没内容 | 用户关注的地区连续两周无新增 | 有变化才推送；全国版内容密度高于单一城市；申报季做专题 |
| 政府网站改版或防护升级 | 失败告警增多 | 改版：配置化规则 + 来源接入 Agent 快速修复。防护升级：停用该来源、找其他官方渠道，不绕过。前台显式展示失败和缺口 |
| 商标被占用 | 商标网近似查询有冲突 | 换备选名「见源」「引据」 |
| AI 说错一个截止日 | 客户投诉截图 | 关键字段只从人工确认过的结构化字段读取；AI 不生成数字 |
| 一人精力不够 | 你每周投入超过计划，客户响应变慢 | 自动化优先；按 G2 关口招人 |
