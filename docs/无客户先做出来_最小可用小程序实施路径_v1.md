# 无客户先做出来：最小可用小程序实施路径

**日期：**2026-09-25  
**定位：**这是[主规格 v5.1](./全行业资料库AI小程序_完整产品与开发主规格_v5.1.md)的**收窄试做路线**。把数据核验、产品设计和通用工程骨架并行推进，尽早得到可在微信真机上试用的一条真实答案链。完整阶段、公开 AI 与商业化门槛仍以主规格为准。当前没有客户，不以访谈、预订单或付费意向作为开始开发的条件；估时取决于人员、站点条件、平台环境和权利确认，均非上线承诺。

## 一、先做成什么样

第一版仅深做“青岛企业认定名单与申报节点”这一组任务，让用户完成：

```text
输入企业/项目或选择问题模板
→ 看结论或明确的无法确认、阶段、日期、适用对象、出处
→ 展开官方附件行/条款和来源健康
→ 保存关注，看到新增/更正/检查失败
→ 只将选中的答案及明细导出 XLSX 或 DOCX
```

“全行业”在第一版是可搜索的**来源与题录分类入口**，不宣称每个行业都有全文问答、每日监测或可下载报告。未来按重复搜索需求、来源可用性与维护成本逐专题加深。完整原文件不进小程序包；只有题录的企业或智库报告只给原站入口和可用状态。

## 二、按什么顺序做

| 时间与并行关系 | 产品/资料工作 | 工程工作 | 阶段交付 |
|---|---|---|---|
| **第 1 周：缩小范围、边核边搭** | 指定实际决策、资料和工程负责人；从 2–3 个官方栏目抽真实公告/附件；做 20 个“问题—预期答案/拒答—原文位置”样本；登记每种资料可否展示题录、解析、AI 阅读与导出 | 建立仓库、环境、登录与 API 骨架、基础数据表；用真实但人工核对的样本搭答案卡与证据页 | 3 张关键页面可操作；每个示例都有真实来源；来源条件与未决项登记清楚 |
| **第 2–3 周：打通数据链** | 核对公示/正式名单的附件行、申报节点不同责任方与更正；给疑难项做人工待核规则 | 来源登记、题录导入/发现、去重、版本、事实和行级证据、查询接口；在访问条件允许时加入轻量栏目检查，否则先人工维护 | 对一批真实样本能稳定给出“有依据/部分覆盖/无法确认”，来源失败不写成无更新 |
| **第 3–4 周：做小程序任务闭环** | 用真实问题核对排序、答案文案和导出样本 | `找答案/关注/文件/我的`基础页面、分类筛选、出处展开、收藏/纠错、所选 XLSX/DOCX 异步导出；服务端检查用户与资料权限 | 微信真机上完成“提问→证据→保存/导出”；文件在目标 Office/WPS 环境打开 |
| **第 4–6 周：加限定 AI 与持续更新** | 扩充拒答、同名、改版、截止日冲突样本；逐条检查 AI 引文是否支持结论；确定运营值守 | 在获权且已核证证据范围内做测试版 AI 解释；按允许的方式监测试点栏目，记录成功/失败与版本；形成运营待核队列和日志 | 受控试用版可供团队及受邀用户操作；连续运行、失败恢复和引用质量有记录；公开 AI 仍按主规格门槛开放 |

**计划假设：**至少有产品/资料负责人、数据/后端工程、微信小程序工程和兼职质检/设计各自承担明确责任；人员不足或附件复杂时，应缩小栏目数或延长时间。平台审核、资料授权和公开发布周期不能由上述周数保证。

## 三、第一版的模块边界

| 必做 | 第一版交付方式 | 何时扩展 |
|---|---|---|
| 资料来源与分类 | 发布方、栏目、地区、行业/主题、类型、最后核查、权利状态；先提供可信入口 | 加行业来源时逐来源审核，不以目录数充覆盖率 |
| 名单、政策、申报结构化 | 用真实官方样本核对名单行、阶段、主体和截止节点；关键事实可回源 | 不同资料类型建立各自提取规则，不靠一个通用 PDF 摘要器 |
| 搜索与答案 | 结构化问题和范围筛选优先；数值、日期、名单由已核事实查询；无法确认要显示缺口 | 自然语言解释及跨文档研究只用获权证据、通过评测后开放 |
| 关注与更新 | 用户确认具体地区/主题/事项；展示新发布、修订、迟到发现、来源失败 | 主动消息按平台能力核验，周期频率按实际事件量调整 |
| 文件 | 选中事实及证据生成 XLSX/DOCX，记录报告版本；文件生成失败可重试 | PDF/PPTX、团队投递和外部应用连接在需求与权限证据形成后增加 |
| 运营后台 | 来源健康、待核事实、用户报错、更正对受影响答案的追踪 | 多行业时按来源数量、异常与复核成本扩容 |

建议的技术切分是：微信小程序负责输入、筛选和结果展示；服务端 API 负责查询、权限、答案和文件；结构化数据库存来源/事实/证据/任务；后台作业负责发现与版本比较；获准的大文件按需要由服务端处理，原件是否缓存按权利决定。腾讯云 CloudBase 的官方文档提供微信小程序访问数据库、存储和云托管服务的能力，可作为部署候选之一，具体架构需结合团队现有运维能力、成本及数据任务选择。[CloudBase 小程序接入文档](https://docs.cloudbase.net/run/develop/access/mini)

## 四、开工和试用分别用什么门槛

**现在即可做：**设计页面状态、搭通用项目骨架、整理人工核对的公开样本、写样本查询和导出流程；这些不需要客户承诺。对某个来源做自动获取、全文保存、AI 阅读或对外再分发前，逐动作确认访问条件与权利。

**进入试用的最低证据：**①至少 20 个真实问题，每个有原站依据或明确拒答理由；②至少一条公示→正式及一条多责任方申报节点能回到原文/附件行；③搜索、保存、导出在微信真机实际走通；④来源失败、附件解析错行、同名企业和更正不产生确定性错误；⑤所选 XLSX/DOCX 在目标办公软件打开；⑥有人负责每日异常和用户纠错。监测若已自动化，则连续检查日志要足以判断漏报与恢复；只做人工更新的栏目明确标“人工维护”，不伪装实时监测。

**公开发布和收费另验：**小程序平台、AI 适用要求、资料权利、隐私、支付、退款、生成内容标识及公开运行质量各自核验；它们影响对应功能上线，不妨碍先做真实的受控试用版。第一批用户可从公开、有出处的样本页和受邀试用获得；记录他们是否能完成任务、复访及愿否为持续任务付费，不能把“做出来”自动等同于“已有市场需求”。

## 五、第一批用户来了以后再决定什么

公开可分享一份有出处、有截止时间的真实样本，邀请行业从业者完成同一个实际查询任务。记录：用户问了什么、是否有覆盖、完成所需时间、是否展开证据、导出后修改多少、是否保存关注、下一期是否回来、人工与模型总成本。把用户提出但当前无覆盖的高频问题放入需求队列，作为第二专题选择依据。收费先试一种交付物或一类持续任务；价格与团队版不凭资料总数推定。
