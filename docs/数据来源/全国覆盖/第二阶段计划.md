## 二、每批怎么做（同一套流程）

1. **盘点**：`youju coverage-inventory --province …`（页面缓存 14 天内不重抓），导航找不到的看是不是脚本导航、年报目录在别处，补导航适配器（第五节），重跑。
2. **试读**：`youju coverage-verify`，按平台分组看读不出的原因；同一平台读不出的，写或改平台适配器（`crawler/adapters.py`），整批重试读。
3. **导入**：`youju import-sources --csv 栏目清单/<省>.csv`，新来源一律 `enabled=0`（"试跑可读"按静态抓取方式导入但不启用）。
4. **试抓**：在抓取机器（创始人本机，见第七节）上 `youju crawl --include-disabled --province …` 抓一轮，看板算状态。
5. **启用**：看板"待启用"里抓取成功的，分批在后台启用；每批记审阅人和试跑凭证（沿用来源接入页的做法）。
6. **验收**：看板按级的覆盖率、触达率达标；"需人工""不能抓"逐格有原因和替代来源说明。

## 三、启用节奏和下游容量

全国铺开后，栏目从现在的 129 个涨到约 4–7 万个。试点两省实测（`试点覆盖报告.md` 第五节）：每格每月约 4.5–7 份新文件，推到全国约 3.5 万格是**每月约 15–25 万份**（现在约 800 份，约 200–300 倍），其中申报通知约 5,000–9,000 份、名单约 5–8 万份。要同步扩的地方：

| 环节 | 现在 | 要改 | 什么时候 |
|---|---|---|---|
| 抓取并发 | `max_workers=8`，每天 2 轮 | 同一网站仍串行、间隔 3 秒，不同网站并发提到 64–128；按网站分组排队（已有）；一轮控制在 1 小时内。集约化平台下一个主机挂几十个栏目（县级门户频道），按盘点结果统计每个主机的栏目数，栏目多的主机先排、单独计时；抓取器的域名解析并发上限是 32，并发提到 64 以上要先加解析缓存（盘点工具里的 `CachingResolver` 可以直接用） | 第 1 周 |
| 抓取位置 | 云托管 admin 服务 | 搬到创始人本机（本机 MySQL），公开数据同步到线上（服务器迁移线负责同步，本线只保证抓取程序能在任何机器上跑） | 第 1–2 周，跟服务器迁移线对齐 |
| 每天新启用来源 | — | 每天新启用不超过 2,000 个栏目，先看一天的新增量、分类和截止日期核对量再放下一批 | 全程 |
| 截止日期核对 | 人工核对申报通知的截止日期 | 申报通知约 5,000–9,000 份/月（一天 170–300 份），人工核不过来：只把"申报通知、30 天内截止"的排进核对台，其余显示"原文摘录、未核对"（现有规则），核对台按截止日排序；转发同一上游通知的各地版本（转发组）只核一次上游 | 第 2 周前 |
| 转发归组（D-055） | 每次全量重算，读全部文件和正文开头 1500 字 | 县级大量"转发……的通知"：改成只算最近 180 天（`MAX_DAYS_APART=90` 的两倍窗口）、增量加入新文件；同一核心标题的桶可能有几千份，要限制两两比较 | 第 3 周（地市铺开前） |
| 分类 | 标题规则入库时算好 | 规则本身够快；试点里"其他"占 29%，AI 分类只用于规则拿不准的，按每月 15–25 万份预估成本后再定是否扩大 | 第 2 周评估 |
| 覆盖看板 | 第一阶段是离线统计 | 看板状态计算放进数据库（按格分批更新），后台页按省分页，不一次读全部 | 第 1 周 |
| 搜索 | 标题 `LIKE '%词%'` 全表扫描（几万份以内足够快） | 文件到几十万份要换全文索引（MySQL ngram），先在本机库量一次 | 第 4 周前 |
| 地区筛选 | 已收录城市、区县按启用且成功过的来源算 | 不变；城市、区县选项会多很多，小程序里的选择器要能搜索 | 第 4 周 |

## 四、读不出的栏目：程序写规则 + 自动试跑

不适合任何平台规则的栏目（预计每省几十个），用现有"来源接入 Agent"（`sources/onboard.py`，D-023）的做法批量处理：

- AI 只看这张政府网页本身的结构，写 CSS 选择器；
- 程序用它在同一页面试跑，识别出至少 3 条带日期的条目、而且条目网址和栏目在同一网站才算可用；
- 可用的规则写进 `parser_config`，状态记"需人工确认"，人在后台看试跑结果点确认后才启用；
- 规则失效（连续 3 次识别不出）自动报警，回到这个流程。

不用 AI 也能先做的：按平台批量写好选择器（同一平台几百个栏目一条规则）。

## 五、导航补齐（门户和部门找不全的省）

第一阶段的通用规则（首页、导航页、页脚脚本、政府网站年度报表目录）在多数省找全了门户；找不全的分三类处理：

1. **省级门户打不开或拦截**（广西、新疆、江西、海南：robots.txt 取不到或连接被断；湖北、甘肃：412 防护）：先在不同时段用同样的透明标识重试；确属拒绝的记"不能抓"，不换标识、不绕过。地市门户另找官方入口（地市门户自己的"兄弟城市""省内各市"导航、省政务服务网的地区导航页），找到的入口写进导航入口补充表，写明来源页。
2. **导航由脚本生成或在别的页面**：写导航适配器（每省一个小函数或一组入口页），如广东"地级以上市网站"页、安徽每个地市一个导航脚本、河南年报目录逐市进一层。
3. **县级部门没有独立网站**：集约化后县直部门多半是门户里的"部门频道"或信息公开目录里的部门栏，按平台写"部门目录"规则（同一平台各县一样）。

## 七、要创始人决定或本人做的

1. **抓取放在哪台机器**：本线按"创始人本机跑抓取、本机 MySQL、公开数据同步线上"设计（和服务器迁移线一致）；本机要能长时间开机联网。
2. **启用节奏**：每天新启用上限（建议 2,000 个栏目）和截止日期核对只排"申报通知 + 30 天内截止"，请确认。
3. **对外怎么说覆盖**：看板验收前，对外只说已验收的层级和省份，不说"全国四级全覆盖"。
4. **不能抓的网站**：保持"不绕过"（不换标识、不用浏览器绕防护），只找官方替代来源，请确认。
