## 用脚本跑（推荐）

控制台贴回来的中文会乱码（10/16 的教训），所以把下面一到三节合成了一个脚本：每一步先试算、核对，对不上就停，每一步只打一行纯 ASCII 的结论。只在前台跑，不要 nohup、不要放后台：

```bash
sh /app/backend/deploy/batch1.sh --check     # 先试算，不改库
sh /app/backend/deploy/batch1.sh --apply     # 创始人点头后再跑
```

用 `sh` 跑，不靠文件的执行权限（上传镜像后执行位还在不在没核实过）。

只看这些行（同时写进 `/tmp/batch1-<时间>.txt`）：

- 第一行 `log=/tmp/batch1-<时间>.txt`：这次的结论文件；细节文件是同名的 `-detail.txt`；
- `step=batch rows=237 expect=237 ... same_as_evidence=1 unknown_verdicts=0 ok=1`：批次文件和证据表一致；
- `step=import_check new=237 expect=237 existing=0 ok=1`、`step=import new=237 expect=237 ok=1`：导入（只加新的）。`existing` 应为 0（批次已去掉线上清单的网址）；不是 0 的是后台"来源接入"加过的同一个列表，网址在细节文件里，不影响导入；
- `step=accept_check lvl=PROV accepted=21 held=8 batch_provinces=21 manual_holds=0 ok=1`：抽查结论。`manual_holds` 是后台"覆盖看板"里人工记了"没过"的省：在本批里的，脚本停下不开；不在本批里的，不盖掉它。第四步看板导入要一两分钟，这期间有人记了"没过"，第五步写之前按最新记录再查一遍，在本批里的也停（`stop=1 step=accept`）；
- `step=coverage_import divisions=... cells=... ok=1`：看板（全国约 4 万格）；
- `step=accept lvl=PROV written=29 already=0 kept_manual=0 ok=1`：记抽查结论（重跑时同一份证据不重记；人工记的"没过"留着，记在 `kept_manual`）；
- 每省一行 `step=enable_check prov=TJ lvl=PROV n=15 expect=15 done_before=0 missing=0 ok=1` 和 `step=enable prov=TJ lvl=PROV n=15 expect=15 ok=1`：分省打开，每省应打开数由批次文件和证据表现算；
- 最后一行 `batch1_done=1 enabled=237 expect=237`。

哪一行 `ok=0`，脚本就打 `stop=1 step=... detail=...` 停下，不往下走；对不上的网址写在同名的 `-detail.txt` 里（中文，拿回来看文件，不看终端）。出了意料外的错，打 `stop=1 step=<哪一步> error=<错误类型> detail=...`，出错经过也在细节文件里。审计行（谁、依据哪条抽查记录打开了哪些来源）除了照常写日志，也写进细节文件。中途停了修好再跑 `--apply`：导入过的跳过、记过的抽查结论不重记、已经打开的算 `done_before`。

下面一到三节是脚本里做的事，脚本跑不了时可以照着一条条跑，每条都用 `2>&1 | tee -a 第1批.log` 留日志（审计行写在 stderr，只 `| tee` 会漏掉）。

## 一、导入来源（新来源一律不启用）

```bash

```

试算要看三样：
- 新增数：应为 237。
- "库里已有的网址"：已经在收的来源，`--only-new` 一律不碰。
- "和库里只差 http/https 等写法的"：同一个列表，不会新建。

批次文件已经去掉了仓库里线上清单的网址，所以后两样应该是空的。出现的是后台"来源接入"页加过的，记下来，不影响导入。没问题再去掉 `--dry-run` 正式导入。

**不要在线上用 `crawl --include-disabled` 试抓**：小程序给用户看的文件不看来源启没启用，一抓进来就对用户可见。试抓已在本机做完（证据见抽查汇总）。

## 四、打开以后

- **每轮变长多少**：本机试抓 417 个栏目 32 个网站并发用了 57 秒；线上 8 个并发，这 237 个栏目每轮大约多 2–3 分钟。每轮补正文仍是最多 600 份，所以一轮不会超过 1 小时。
- **基线入库**：下一轮抓取（6:30 / 20:30）会抓这些栏目。第一次抓会把列表页上现有的条目记成基线入库，标题、日期、链接马上能在小程序里看到。按本机试抓，这 237 个栏目 4,567 条，其中近 30 天发布的 1,175 条。
- **正文**：线上每轮补 600 份、每天 1,200 份，4 天左右补完。建议手动先补近 30 天的（1,175 条），这一步不在脚本里，单独跑：
  - 什么时候：打开以后要等下一轮（6:30 或 20:30）抓过列表，才有这批文件。所以是那一轮之后的白天，比如白天打开、当晚 20:30 抓过，就是第二天白天。
  - 用 `/app/backend/deploy/job.sh fetch-details --limit 1300 --workers 4 --since <30 天前的日期>`，不要直接 `youju fetch-details`。job.sh 和每轮里的补正文共用一把锁，不会两边同时跑、重复抓同一批；还会记进任务记录。
  - job.sh 的输出写进容器日志（云托管日志里看"开始：youju fetch-details…""完成：…"），终端上 15–25 分钟什么都不显示，等它自己返回。要是马上返回、退出码 75，说明一轮正在补正文（同一把锁），过一会儿再跑；这时会发一条"任务 youju fetch-details 失败：退出码 75（上一次还没跑完，本次重叠跳过）"的提醒，可以不管。
  - 时间避开 6:30、20:30 两轮（每轮从开始到补完正文要几十分钟），也避开 10:15 的 cache-attachments 和 10:45 的 list-evidence（它们也读 PDF），比如 14:00–17:00。
  - 资源：admin 容器 2GB。每个进程只放 1 个读 PDF 的子进程（pdf_sandbox 的 PARALLEL=1，每个最多 1GB、实测多在 100MB 以内），所以要和别的读 PDF 的任务错开；4 个抓取线程大部分时间在等网络和同一网站 3 秒的间隔，不会把 CPU 撑满。
  - 用时：1,175 条分在 143 个网站（按文件网址算），最多的一个网站 38 条（3 秒一条约 2 分钟），加上 PDF 排队读，估计 15–25 分钟。
- **原网页检查**：每天最多查 3,000 份、只查近 90 天，这批上线后会多出一批。输出里"该查还没轮到"连续几天不是 0，就调大 `--limit`。长期方案见第二阶段计划第九节。
- **看板**：跑 `youju coverage-refresh` 后，省级应以"已收录"为主；"抓取失败"的格点开看原因。

## 五、回滚

1. **停用来源**：在后台"来源接入"逐个停用；整批停用用下面这句。它只停这一批打开的，这批来源的备注里都写了"全国覆盖：××抽查合格（抽查记录 #n）后由 … 启用"。

   ```sql
   UPDATE sources SET enabled = 0 WHERE note LIKE '%全国覆盖：%抽查合格（抽查记录 #%';
   ```

2. **补记"没过"**：在后台"覆盖看板"给回滚的省记一条抽查"没过"。回滚后这些来源有成功记录、名下有文件，抽查记录要是还是"合格"，下次跑 `coverage-enable` 会把它们重新打开。
   回滚以后不要再跑 batch1.sh 去"补"：脚本不会盖掉人工记的"没过"，在本批里的省会在 `accept_check` 停下（`manual_holds` 不是 0）。修好以后要重新放，先重新抽查、改证据表、重生成批次，再在看板记"合格"，然后再跑。
3. **已入库的文件**：不会自动消失，要下架按现有下架流程。
